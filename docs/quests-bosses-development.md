# Квесты, категории и ивент-боссы

Общий itemSlug обеспечивает автогенерацию, транслитерацию и ручное редактирование. Описание — richText с общим Lexical. Изменение/удаление доступны только Users; чтение quests/bosses открыто на этапе публичного каталога items, quest-categories остаётся закрытой. Quests, quest-categories и bosses имеют штатный ручной порядок, в запросах `sort: '_order'`. Development schema push сохранён. Users, Media, зависимости и фронтенд не меняются.

## Текущая модель квеста

- name, slug, description, coins; монеты — безопасное целое ≥ 0, по умолчанию 0.
- category — необязательная связь с одной quest-categories.
- requiredQuantity — необязательное число «Необходимое количество», пояснение «Сколько нужно собрать, добыть или выполнить для завершения квеста». Если заполнено — положительное безопасное целое. DefaultValue нет; отсутствие/null допускается, 0 не допускается. Это условие выполнения, не награда.
- cooldown — необязательный text «КД прохождения», например «6 часов» или «Раз в сутки». Значения по умолчанию нет. Свободная справочная информация, без персональных таймеров.
- rewards — прежний список resource + quantity; ordinaryRewards — отдельный список item → ordinary-items + quantity. Количества положительные безопасные целые, ссылки существуют; внутри каждого списка нет дублей. Ресурс и обычный ресурс с одинаковыми числовыми ID допустимы в разных списках.

Расписание, цепочки, требования принести отдельные предметы и связи с events/bosses не добавлены. PATCH проверяется вместе с исходным документом, массивы наград заменяются независимо и не очищаются при изменении КД/количества/категории.

## Категории и обратный список

Quest-categories имеет обязательные name и уникальный slug с общей транслитерацией. Единственная хранимая связь — quests.category. Штатное join-поле quest-categories.quests использует `collection: 'quests', on: 'category'`, `defaultSort: '_order'`, без отдельного редактируемого массива. Встроенная пагинация не ограничивает общее количество квестов категории. Создание из join отключено; назначение категории меняется в квесте. Используемую категорию нельзя удалить до снятия/замены всех ссылок.

## Безопасный переход КД в текст

Перед изменением конфигурации выполнен SELECT в PostgreSQL в транзакции READ ONLY. На момент проверки 2 ноября 2026 найдены два квеста (ID 1 и 2), у обоих cooldown_minutes = 0. Схема и данные проверкой не изменялись.

Нельзя просто заменить тип существующего cooldownMinutes или удалить колонку при development schema push. Реализован переход с сохранением старой колонки:

1. Новое необязательное текстовое поле — cooldown. Старое cooldownMinutes остаётся числовым, скрытым в админке, без обязательности и defaultValue. При schema push нужно добавить cooldown и required_quantity, сохранить cooldown_minutes, снять с неё NOT NULL/default. Не соглашаться на удаление старой колонки или сброс таблиц.
2. До первого сохранения afterRead возвращает текст из прежнего числа с явной единицей: 360 → «360 минут», 0 → «0 минут». Исходное число при чтении не изменяется. При запросах с select только cooldown для немигрированных записей нужно также выбирать cooldownMinutes, иначе исходное число не попадёт в hook. Обычные полные чтения и формы получают оба поля.
3. При обычном сохранении/PATCH beforeValidate переносит прежнее значение в cooldown, если новое не задано, не перезаписывая существующий текст. Старое число очищается только в том же сохранении, где записывается текст; Payload выполняет сохранение атомарно. ID, slug, награды и связи не меняются. Это отложенный перенос по мере сохранения записей, а не уже выполненный массовый backfill.
4. Явное пустое значение/очистка cooldown сохраняется: старые минуты не должны появиться заново. Новая запись без КД не получает «0 минут» автоматически.
5. Колонка cooldown_minutes пока сохраняется. Удалить её можно отдельным согласованным этапом после проверки переноса всех записей и резервного копирования. В этом этапе миграции Payload и SQL-изменение схемы вручную не вводятся.

На текущей базе перенос не запускался и schema push агентом не применялся. После следующего запуска development старые значения доступны в текстовом поле через совместимость; для физической записи текста нужно сохранить квест. КД events и его проверки не меняются.

## Боссы и целостность

Bosses: name, slug, необязательные image/description, coins ≥ 0 по умолчанию 0. Награды хранятся в стандартном массиве `rewards`: обязательный resource → resources («Кастомный предмет»), обязательное положительное безопасное целое quantity по умолчанию 1. Нет ограничения двумя предметами и требования определённых сердец; список можно оставить пустым. Дубли одного предмета и несуществующие ссылки запрещены. PATCH без rewards сохраняет массив; явный массив заменяет его целиком. Расписания и связи с events нет.

Удаление resources блокируется рецептами, наградами events/quests и `bosses.rewards.resource`. До завершения переноса также учитываются прежние скрытые ссылки боссов. Ordinary-items дополнительно защищены quests.ordinaryRewards.item; категории — quests.category. Каскадного удаления игровых записей нет. Защита изображений отложена. Все вложенные запросы передают req; ограничения гонок стандартных хуков сохраняются.

Безопасный перенос прежних ссылок, массовый backfill и проверки описаны в [boss-rewards-transition.md](boss-rewards-transition.md). Старые колонки остаются в схеме на этом этапе; бизнес-правило двух обязательных разных сердец удалено.

## Проверка и ручной сценарий

Выделенная тестовая база подключена, проверки выполнены; подготовка изолированных проверок описана в [model-verification.md](model-verification.md). Пользователь подтвердил ручную проверку основных коллекций. Проверки с записью в текущую базу не выполняются. Изолированные тесты проверяют хуки с подставленными ответами поиска; они не доказывают сохранение через Payload/PostgreSQL или отображение живого join. Генерация типов проверяет допустимость конфигурации join.

После применения development schema push пользователь проверяет на собственных записях:

1. Открыть старый квест: прежний КД виден как «0 минут» (или число минут с единицей). Сохранить, переоткрыть; проверить награды и категорию. Ввести «6 часов», затем «Раз в сутки», затем очистить — старые минуты не должны вернуться. В новой записи пустой КД остаётся пустым.
2. Оставить «Необходимое количество» пустым, сохранить; затем проверить положительное целое. Значения 0, отрицательное и дробное должны отклоняться. Очистка поля должна сохраняться без подстановки 0. Количества наград не меняются.
3. Открыть категорию и проверить список её квестов. Назначить квесту другую категорию, обновить оба списка; очистить категорию и проверить исчезновение из списка. Для большого списка проверить страницы join.
4. Проверить оба списка наград и их прежнюю валидацию дублей/количеств. Попробовать удалить используемые категорию и обычный ресурс — получить понятную ошибку. После снятия всех ссылок удаление доступно, если нет других использований.
5. Проверить ручной порядок категорий и квестов после перезагрузки. Убедиться, что КД ивента по-прежнему числовой.

На выделенной тестовой базе дополнительно проверить через Payload API: перенос старых минут при PATCH других полей; явную очистку КД и количества; null/отсутствующие значения; сохранение обоих массивов наград; получение join с пагинацией и изменение его состава после переноса категории; access control с overrideAccess: false; запреты удаления и отсутствие каскадного удаления.

Итоговая проверка через тестовую PostgreSQL выполнена; прямые обратные запросы с пагинацией работают. Штатная пагинация join на третьей странице имеет подтверждённый дефект адаптера 3.92.1. Подробности, обход прямыми запросами и ожидаемые падения тестов: [model-verification.md](model-verification.md).

Уточнение native join: сет из семи вещей полностью возвращается при текущем defaultLimit = 10. Для больших наборов стандартные списки с фильтром по equipmentSet/category используют прямые запросы; не следует автоматически считать их затронутыми дефектом native join. Минимальное воспроизведение, проверенный серверный findEvents и ограничения обходов: [model-verification.md](model-verification.md).

Актуальная публичная политика чтения и скрытие неактивного recipe на этапе /items описаны в frontend-plan.md (третий этап); исходные админские сценарии и правила записи/удаления сохранены.

Актуализация публичного этапа квестов: quest-categories открыта для чтения; запись/удаление остаются только Users. Каталог и детали quests реализованы, без расписания. Типизированные награды в фильтре различаются по kind:id; старые указания о закрытом чтении категорий относятся к предыдущим этапам. См. frontend-plan.md, девятый этап.
