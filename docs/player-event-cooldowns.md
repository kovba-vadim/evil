## Модель и операции

Коллекция `player-event-cooldowns` хранит одну текущую запись на пару `player` + `event`; уникальный составной индекс создаёт штатный PostgreSQL-адаптер Payload. Поля: связи, `completedAt`, `cooldownUntil` (UTC), `cancelled`, серверная `revision` и скрытый `requestID`. Истории нет.

КД берётся только из реального `events.cooldownMinutes`, единица — минута. Начало — серверное время после получения блокировки; конец = начало + минуты. Изменение ивента не пересчитывает сохранённый конец. Следующее прохождение после завершения использует новое значение и обновляет ту же запись.

Ноль и отсутствующее legacy-значение явно означают отсутствие личного КД: `cooldownUntil = completedAt`, прохождение сохраняется, в активный список не попадает. UI объясняет отсутствие КД и разрешает новую отметку. Отрицательные, дробные и выходящие за диапазон даты значения не подменяются: запись отклоняется.

`POST /api/account/cooldowns` принимает:

- `action: complete`, `eventID`, UUID `requestID`, `previousRevision` (null при отсутствии записи).
- `action: cancel`, `eventID`, `revision` текущей отметки.

Клиент не задаёт игрока, начало, конец или длительность; посторонние поля отклоняются. Игрок определяется по HttpOnly-сессии. Версия — только условие согласованности, не источник времени. Смена пароля, вход и админка не менялись.

Каждая операция использует транзакцию Payload и `pg_advisory_xact_lock(hashtextextended(...))` на пару игрок–ивент через текущую Drizzle-сессию PostgreSQL. Единственный SQL — получение блокировки; таблицы и контент создаются/меняются только через Payload. Все CRUD проходят с `overrideAccess:false`, игроком и общим req/transactionID. Исключение — узкое доверенное чтение скрытого requestID уже найденного собственного документа, с обоснованным overrideAccess:true.

Одновременные запросы сериализуются между Node-процессами. Активная отметка возвращается без изменения. При нулевом/завершившемся КД новая отметка требует актуальную версию; конкурирующая устаревшая версия получает 409. Повтор текущего requestID не меняет время. Отмена сбрасывает cancelled=true и сохраняет последний requestID: его запоздавшая повторная доставка не воссоздаёт отменённый КД. Новая отметка получает новую revision; старая отмена не затрагивает её. requestID последнего запроса хранится только в текущей записи, не образует историю; версия защищает от старых запросов после следующих отметок.

## Доступ и кэш

Стандартный REST/GraphQL Payload может читать только собственные записи игрока. Guests/Users не читают персональный список; связи имеют maxDepth:0, приватные данные Players не раскрываются. Прямые create/update/delete закрыты, включая попытки игрока изменить собственные даты/владельца. Изменения разрешены только серверной операции с внутренним Symbol-capability, недоступным JSON-клиенту. Коллекция скрыта в админке, игроки не получают административный доступ. Хуки дополнительно защищают запись и удаление даже при ошибочном доверенном CRUD без capability.

`GET /api/account/cooldowns` возвращает все активные записи с полной пагинацией и сортировкой по ближайшему окончанию. `?eventID=...` возвращает текущее состояние конкретного ивента, включая завершённую/отменённую запись. Поля ответа перечислены явно, requestID не возвращается. Чтение текущего состояния и запись используют серверную сессию; ответы имеют `Cache-Control:private,no-store,max-age=0`, Vary:Cookie. SSR кабинета/ивента динамический, данные не кладутся в общий кэш.

POST требует точный Origin и JSON, ограничивает тело 1024 байтами при чтении потока; лимиты — 600 операций на процесс и 120 на игрока за 15 минут. Сохраняется существующее ограничение инфраструктуры: счётчики запросов в памяти Node, хотя целостность КД и блокировки общие через PostgreSQL. GET выполняется при загрузке и возвращении на вкладку; он не пишет данные.

## Интерфейс

В детали `/events/[slug]` есть «Мой КД» и кнопка «Прошёл»; гостю показана ссылка входа с возвратом на этот ивент. Активный таймер показывает остаток, дату/время конца и отмену с подтверждением. После конца — «КД закончился» и новая отметка; никакой гарантии наличия/занятости ивента нет.

В `/account` добавлен раздел «Мои КД», ссылки на ивенты, отмена и пустое состояние. Завершившиеся записи исчезают из активного списка без перезагрузки. Персональные данные остаются в БД после выхода и доступны другому устройству с тем же аккаунтом.

Отсчёт использует существующий useServerClock: серверный timestamp + фактическое monotonic elapsed время, без доверия Date.now устройства и числа срабатываний таймера. Focus, visibilitychange и pageshow перечитывают сервер. На время повторной проверки персональный снимок скрыт; при другой сессии очищается, при ошибке остаётся скрытым до успешного обновления. Устаревшие ответы GET прерываются/отбрасываются; двойная отправка блокируется, при ошибке успех не показывается, requestID сохраняется для повтора. Обновление между устройствами при возвращении на вкладку; WebSocket и фоновый polling не добавлены.

Сохранённая зона игрока используется для SSR и как начальная зона; дальше применяется общий time-zone store, включая сохранение профиля и ручной выбор в расписании. Форматирование — существующий formatLaunch с IANA/DST; UTC-моменты не пересчитываются при смене зоны. Новые БЭМ/SCSS-стили используют существующие цвета и адаптивность; зависимостей нет.

## Ручная проверка

1. На `http://localhost:3000/events` выбрать существующий ивент. Гостю предложен вход; после входа возврат на его `/events/[slug]`.
2. Нажать «Прошёл»: остаток и дата окончания, кнопка повторного прохождения скрыта. Перезагрузить: конец тот же. В `/account` запись в «Мои КД».
3. Открыть второй браузер с тем же аккаунтом: отметка доступна. Отменить с подтверждением в первом; вернуть фокус второму — состояние обновляется. Другой игрок её не видит.
4. После окончания увидеть «КД закончился» в детали и исчезновение из кабинета без reload. Новая отметка использует актуальный КД ивента. Нулевой КД сохраняет факт без активного таймера.
5. Проверить зону профиля, ручную смену зоны, обе темы, клавиатуру и телефон. Ошибка сети не должна выглядеть успешным сохранением; после ошибки перечитать данные.
6. Проверить обычный вход/редактирование профиля/смену пароля и вход администратора. Не менять рабочие ивенты ради теста; крайние сценарии уже проверяются фикстурами изолированной базы.
