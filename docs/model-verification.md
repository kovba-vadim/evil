# Итоговая проверка модели

## Результат этапа проверки модели (до публичного каталога)

Пользователь подтвердил создание основных коллекций и ручную проверку админки. Это не подтверждает сложные PostgreSQL-запросы, пагинацию, права и целостность через Local API. Новые поля, публичные маршруты и фронтенд в этом этапе не добавляются.

Сверка кода: ordinary-items — «Обычные ресурсы» с необязательным описанием Lexical; resources — «Кастомные предметы». Bosses использует rewards (resource + положительное целое quantity, default 1), без фиксированного числа наград. Старые ссылки временно скрыты для безопасного переноса. Quests имеет одну необязательную category, текстовый cooldown, необязательное положительное целое requiredQuantity без default и два независимых массива наград. Events хранит ежедневное расписание отдельно от числового КД в минутах. Подключение к PostgreSQL остаётся в режиме development schema push.

Тестовая база и роль созданы пользователем; подключение через EVIL_TEST_DATABASE_URL проверено. Выполнены проверки через Payload/PostgreSQL только на этой базе. Рабочий DATABASE_URL не менялся, рабочий адаптер не подключался. Schema push выполнялся только в тестовой базе; схема рабочих коллекций в коде не менялась.

Итог: 26 обычных сценариев модели прошли; четыре отдельных it.fails воспроизводят известный дефект штатной пагинации join в адаптере 3.92.1. Их ожидаемое падение не считается исправлением дефекта. Подробности ниже.

## Создание отдельной PostgreSQL-базы

Без Docker. Через SQL Shell (`psql`), подключённый к служебной базе postgres администратором PostgreSQL, выполнить:

```sql
CREATE ROLE evil_test_user LOGIN;
\password evil_test_user
CREATE DATABASE evil_model_test OWNER evil_test_user;
```

`\password` интерактивно запросит новый пароль без вывода. Роль не должна быть суперпользователем и не должна получать права на таблицы рабочей базы. Если используются ограничения pg_hba.conf, разрешить этой роли локальное подключение именно к evil_model_test по принятому на машине способу аутентификации. Таблицы создаёт Payload, вручную их создавать не нужно.

В локальный игнорируемый `.env` добавить (пароль URL-кодировать; реальные значения не публиковать):

```dotenv
EVIL_TEST_DATABASE_URL=postgresql://evil_test_user:URL_ENCODED_PASSWORD@127.0.0.1:5432/evil_model_test
```

DATABASE_URL не заменять. Тестовый URL не должен содержать query-параметров или fragment; имя базы должно заканчиваться на `_test` и отличаться от имени рабочей базы независимо от хоста/пароля. Рабочий DATABASE_URL нужен только для проверки различия имён. PAYLOAD_DROP_DATABASE и PAYLOAD_MIGRATING не должны быть true, NODE_ENV не должен быть production. Тестовый адаптер отключает автоматическое создание базы: её нужно создать заранее указанной командой.

После подключения:

```powershell
pnpm test:model
```

Команда использует отдельный `vitest.payload.config.mts`, Node environment и одного worker без параллельного запуска файлов. `tests/helpers/testDatabase.ts` проверяет изоляцию до импорта конфигурации, создаёт отдельный экземпляр Payload и явно заменяет только тестовый адаптер. Рабочий DATABASE_URL остаётся неизменным. При отсутствии/небезопасном URL команда завершается до подключения с сообщением без реквизитов.

Первый запуск применит штатный development schema push только в тестовой базе. Использовать отдельную базу исключительно для этих тестов, не заполнять её рабочими данными. Сброс/удаление базы не выполняются. После изменения модели вручную просмотреть любые предложения о разрушительном изменении даже на тестовой базе; автоматического подтверждения таких действий нет.

## Выполненные проверки через Payload

`tests/payload/model.payload.spec.ts`:

- Совместный фильтр events: включительные границы 08:00–10:00, запуск 09:55, исключение пары 07:00/11:00; переход 23:00–02:00; требование ВСЕХ выбранных кастомных предметов, включая minQuantity = 0; включительные границы монет, ноль и отсутствие отдельных ограничений; все группы одновременно.
- Четыре подходящих времени и четыре ивента при странице размером 2; один ивент с несколькими подходящими запусками возвращается один раз; отсутствие подходящих времён даёт пустой результат. Равные начало и конец намеренно не закрепляются тестом как продуктовое решение.
- Источники кастомного предмета через rewards.resource в events, quests, bosses; использование обоих типов ингредиентов в resources, clothing, weapons, включая неактивные рецепты.
- Состав сета и квесты категории через прямые обратные запросы с несколькими страницами и штатные join с limit: 0; перенос части между сетами, перенос квеста между категориями и очистка связей.
- Запрет удаления по каждому из источников наград, обоим ингредиентам каждого типа рецепта, времени в нескольких ивентах, используемому сету, категории и обычным наградам квестов. После снятия ссылок удаляется только выбранная запись; связанные документы остаются.
- Анонимные read/create/update/delete всех десяти игровых коллекций с overrideAccess: false; чтение с реальным пользователем тестовой коллекции Users. Запросы и обычные изменения тестового пользователя используют false. True используется явно только для доверенной подготовки/очистки фикстур.
- Перенос старого числового КД квеста при PATCH, явная очистка без возврата минут; сохранение текстового КД и необходимого количества при PATCH; отклонение нулевого/отрицательного/дробного/небезопасного количества; явная очистка и сохранение наград.

Алгоритм первоначально находился только в tests/helpers/eventFilter.ts. Теперь `src/queries/findEvents.ts` экспортирует `findEvents(options): Promise<Event[]>` и типы `EventFilters`, `FindEventsOptions`; прежний тестовый алгоритм удалён. В tests/helpers/eventFilter.ts остался только универсальный helper обратных запросов readAll. Существующие сценарии фильтра непосредственно вызывают серверную функцию со страницей 2.

Функция принимает готовый Payload, фильтры from/to (минуты сервера UTC+3), resources, coinsFrom/coinsTo, необязательный where, user/req и ОБЯЗАТЕЛЬНЫЙ overrideAccess. Не инициализирует подключение и не содержит HTTP-маршрута/Server Action. Каждый Local API вызов явно получает выбранный overrideAccess и user/req. Для действий пользователя нужен false; сама функция не меняет политику доступа. На последующем этапе каталога чтение events открыто публично, event-times остаётся закрытой коллекцией. Все страницы времён, каждого промежуточного запроса по предмету и итогового результата читаются до hasNextPage = false; pageSize по умолчанию 100 — размер страницы, а не предел результата. Результат имеет depth: 0 и стабильную сортировку по id.

Для ВСЕХ предметов функция выполняет отдельный запрос на каждый ID с пересечением ID ивентов. Один AND с несколькими equals по rewards.resource на установленном PostgreSQL-адаптере относится к одной строке массива и неверен для разных ID. Этот вариант больше не используется.

Пример будущего серверного вызова (получение Payload остаётся ответственностью вызывающего кода):

```ts
const events = await findEvents({
  payload,
  user,
  overrideAccess: false,
  filters: { from: 480, to: 600, resources: selectedItemIDs, coinsFrom: 100 },
})
```

Четыре отдельных it.fails сохраняют воспроизведение дефекта native join: минимально три документа при limit: 1 и page: 3; по пять документов при limit: 2 для parts и quests; 21 документ при текущем default limit: 10. В установленном адаптере смещение вычисляется как `(page - 1) * (limit + 1) - 1`, третья страница пропускает пятый документ. Правильные результаты подтверждены прямыми обратными payload.find с полной пагинацией и join без лимита (limit: 0). Код библиотек, зависимости, типы коллекций и интерфейс админки ради обхода не менялись. Прежнее общее утверждение, что постраничная админка обязательно подвержена этому дефекту, уточнено: для текущих однотипных join таблица UI использует прямой payload.find, а не native join пагинацию; живой UI в этой проверке не запускался; после будущего согласованного исправления адаптера ожидаемые падения нужно превратить в обычные тесты.

Каждый тест использует уникальный префикс и временного пользователя. Очистка удаляет только зарегистрированные ID фикстур; не выполняет широких удалений и не трогает существующие документы. Общие уникальные времена, если они уже есть в тестовой базе, могут быть прочитаны, но не изменяются/удаляются. Тест удаления времени создаёт отдельную свободную запись. При прерывании процесса фикстуры могут остаться только в тестовой базе; очистка после аварийного завершения не гарантируется.

Дополнительно успешно выполнена проверка старых наград боссов — существующий `tests/int/bossRewardsPayload.int.spec.ts`, теперь с тем же защищённым адаптером. При настроенной тестовой базе её можно запустить отдельно:

```powershell
pnpm exec vitest run tests/int/bossRewardsPayload.int.spec.ts --config vitest.config.mts
```

## Найденные проблемы подготовки проверок

- `.env.example` содержал устаревший MongoDB URL при PostgreSQL-адаптере; пример исправлен без изменения локальных секретов.
- Шаблонный api.int.spec.ts инициализировал Payload на рабочем конфиге, что могло запускать schema push даже при одном чтении. Теперь он пропускается без тестового URL и использует защищённый тестовый адаптер.
- Старый тест наград боссов сравнивал URL строками и временно заменял DATABASE_URL. Теперь проверяется имя базы независимо от хоста/учётных данных, query-параметры отклоняются, рабочая переменная не меняется.
- Неправильный алгоритм фильтра с несколькими AND по одному пути массива исправлен на отдельные запросы и пересечение ID, проверен через PostgreSQL с пагинацией.
- Подтверждён дефект штатной join-пагинации адаптера; он сохранён как явное ограничение и ожидаемые падения, а не скрыт успешным общим статусом.
- Параллельные test:int запускали конкурирующие schema push в одной тестовой базе. В vitest.config.mts отключён fileParallelism; последовательный полный запуск успешен.
- Legacy-фикстура босса передавала в adapter.updateOne только изменённые поля; адаптер делает upsert и требовал обязательные колонки. Фикстура исправлена на полный документ; чтение старых ссылок и повторный перенос успешно проверены через Payload.
- Документация содержала старое «все пять коллекций», неподтверждённые будущие шаги для уже созданных коллекций и семь описаний Lexical вместо восьми. Описания актуализированы; исторические заметки отделены от текущего состояния.

## Ограничения

Обычные сценарии фильтра, обратных запросов, запретов удаления и доступа проверены через Payload/PostgreSQL. Native join-пагинация при переходе к третьей странице не исправлена. Нельзя переносить этот вывод на все пути UI: установленная RelationshipTable/buildTableState для однотипных связей использует прямой payload.find. Ручная проверка пользователя учтена отдельно.

Гонки конкурентного сохранения/удаления, защита Media, REST/GraphQL и e2e в этой проверке не покрываются. Старые e2e seed-хелперы используют обычный конфиг и не должны запускаться на рабочей базе; команда pnpm test:model их не запускает. Равные границы времени и интерфейс часовых поясов остаются отдельным решением. Завершение backfill боссов/КД и удаление legacy-колонок требуют отдельной проверки данных; ручная проверка форм не доказывает массовый перенос.

## Уточнение native join: воспроизведение, семь вещей и обход

Минимальные проверенные условия: Payload/@payloadcms/db-postgres 3.92.1, обычное неполиморфное join-поле (`parts` → clothing.equipmentSet или `quests` → quests.category), три связанных документа, limit: 1, page: 3, стабильный sort: id, без конкурентных изменений. Третья страница должна содержать третий документ, но пуста. При limit L первая ошибка смещения возникает на page 3: `(page - 1) * (L + 1) - 1` даёт `2L + 1` вместо `2L`; нужен как минимум `2L + 1` связанный документ, чтобы увидеть пропуск. При L=2 это пятый документ; при L=10 — двадцать первый.

```ts
await payload.findByID({
  collection: 'equipment-sets', id: setID, depth: 0,
  joins: { parts: { limit: 1, page: 3, sort: 'id' } },
  user, overrideAccess: false,
})
```

Оба join-поля сейчас не переопределяют defaultLimit. Backend использует 10; стандартная RelationshipTable берёт field.defaultLimit либо admin.pagination.defaultLimit связанной коллекции (у clothing и quests сейчас 10). Реальный сохранённый пользовательский размер страницы в рабочей админке не проверялся: рабочая база не открывалась. На тестовой базе создан сет из СЕМИ вещей: обычный findByID без явных joins/limit вернул все семь, hasNextPage = false; прямой список clothing с limit 10 тоже вернул семь. Поэтому при текущем default 10 такой сет дефектом не затронут. Искусственное уменьшение страницы до 1 или 2 изменяет условия.

При изучении установленных исходников обнаружено существенное уточнение: @payloadcms/ui RelationshipTable вызывает table-state; buildTableState для НЕполиморфной коллекции использует прямой payload.find с фильтром, page и limit. Для текущих parts/quests это отдельный путь от ошибочного native join в findByID. Соответствующие прямые запросы с несколькими страницами проверены. Живая стандартная админка на большом наборе здесь не автоматизировалась; утверждение о гарантированной потере записей именно в ней из прежнего отчёта снято.

Минимальный обход без изменения зависимостей и без собственного интерфейса:

1. Для сета из семи вещей оставить текущий размер 10; увеличивать его не требуется. Это наблюдение о размере набора, а не исправление адаптера.
2. Для больших наборов использовать стандартный список «Одежда» со встроенным фильтром equipmentSet = выбранный сет, или «Квесты» с category = выбранная категория. Эти поля уже доступны для фильтрации; новая конфигурация/интерфейс не нужны. Прямой payload.find с тем же условием и обычной пагинацией проверен и не использует дефектное смещение native join.
3. Если серверному коду нужен именно полный native join небольшого известного набора, явно задать joins.parts.limit = 0 (или joins.quests.limit = 0). Полный join проверен, но загружает весь список; это обход с расходом памяти, а не исправление и не рекомендация для произвольно больших наборов.
4. Явное повышение field.defaultLimit до значения, вмещающего известный набор, — только временный обход. При росте данных до третьей страницы дефект вернётся. Настройки лимита в этом этапе НЕ менялись.

Остались ограничения: native join-ошибка; отсутствие нагрузочной проверки больших ID-пересечений и защита от гонок между несколькими чтениями. findEvents собирает все совпадения в память, выполняет дополнительные запросы по предметам и передаёт ID через in; для очень больших каталогов может понадобиться отдельная оптимизация. Функция принимает доверенные типизированные фильтры; разбор и полная валидация будущего HTTP-ввода не реализованы. Равные границы времени ещё не согласованы как продуктовое поведение (текущие сравнения соответствуют точной минуте), часовые пояса не пересчитываются. Для согласованного снимка вызывающий код может передать req с подготовленной транзакцией/нужным уровнем изоляции; функция не создаёт транзакцию автоматически. Сортировка ответа сейчас по id, будущая сортировка интерфейса отдельна. Рабочая база и настройки пользовательских предпочтений в ней не проверялись и не менялись.

## Обновление при реализации каталога

Текущие проверки доступа учитывают публичное чтение resources, ordinary-items, events, quests, bosses, clothing и weapons. Чтение event-times, equipment-sets, quest-categories и Users анонимно запрещено; запись во все игровые коллекции остаётся только Users. На публичном этапе квестов quest-categories открыта для чтения; анонимные create/update/delete по-прежнему запрещены. Весь игровой каталог теперь имеет явно разрешённое публичное чтение, Users закрыта. Новые тесты типизированных наград/пересечения ID и ограничения описаны в девятом этапе frontend-plan.md.
