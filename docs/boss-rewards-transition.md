# Награды боссов: безопасный переход

## Модель и границы изменения

`ordinary-items` — «Обычные ресурсы» / «Обычный ресурс», с необязательным `description` типа richText и глобальным Lexical. `resources` — «Кастомные предметы» / «Кастомный предмет». Технические slug, имена существующих таблиц и связей не переименованы. В рецептах обновлены только подписи; структура и проверки не менялись.

В bosses добавлен стандартный array `rewards` («Награды») с обычной кнопкой добавления строк Payload. В строке обязательные `resource` → resources и `quantity` — положительное безопасное целое, defaultValue 1. Дубли проверяются по ID, включая populated-значения. Список не ограничен двумя строками, допускает отсутствие наград и явную очистку. Монеты остаются отдельным полем. Доступ и ручной порядок сохранены.

## Почему старые колонки пока остаются

В `postgresAdapter` проекта `push` не переопределяется, файлов миграций и prodMigrations нет. Установленный адаптер выполняет development schema push вне production, если `PAYLOAD_MIGRATING !== 'true'` и `push !== false`. Миграции в этом этапе не вводятся.

Удаление полей из конфигурации до переноса могло бы удалить `bosses.golden_heart_id` и `bosses.personal_heart_id` при push. Поэтому `goldenHeart` и `personalHeart` временно остаются relationship-полями без required/defaultValue, скрытыми и readOnly в админке. Они служат только совместимости, не задают текущие игровые правила. В админке редактируется один список rewards.

Перед запуском новой конфигурации остановить dev-сервер и сделать резервную копию PostgreSQL. При последующем `pnpm dev` проверить предлагаемый schema push: добавить description в ordinary-items и таблицу массива rewards для bosses, сохранить обе старые колонки и снять с них NOT NULL. Не подтверждать переименование существующих таблиц/связей, удаление старых колонок, очистку таблиц или сброс базы. Production-схема этим этапом не развёртывается.

## Чтение и сохранение старых записей

`src/hooks/bossRewards.ts` реализует переход:

1. При чтении старые ссылки добавляются к rewards с количеством 1 только для отсутствующих ID. Уже заданные количества, порядок и ID строк сохраняются. Одинаковые старые ссылки дают одну строку. Чтение не пишет в базу.
2. `forceSelect` выбирает rewards и обе старые ссылки даже при ограниченном select, чтобы отображение не зависело от выбранных колонок.
3. Field beforeValidate переносит старые ссылки до подстановки Payload сохранённого массива в данные PATCH. Collection beforeValidate очищает старые ссылки только вместе с записью нового массива. Валидация и запись выполняются обычной операцией Payload; при ошибке новое состояние не сохраняется.
4. Явно переданный rewards, включая [] или null, заменяет показанный список; это позволяет удалить награды без их повторного появления. PATCH других полей переносит и сохраняет прежние награды. Повторное сохранение не добавляет дубли.
5. До завершения переноса защита удаления resources проверяет новый массив и обе старые ссылки. Остальные запреты удаления сохранены.

Это обеспечивает отложенный перенос при сохранении через админку/API. Он не означает, что все существующие записи уже физически перенесены.

## Массовый перенос

Подготовлен `scripts/migrate-boss-rewards.ts`. После безопасного применения добавочной схемы остановить редактирование боссов на время переноса. Не запускать скрипт до создания таблицы массива. Скрипт отключает собственный schema push через PAYLOAD_MIGRATING, не выполняет миграций схемы и использует текущее подключение из .env. Не включать PAYLOAD_DROP_DATABASE.

Проверка количества записей без переноса:

```powershell
pnpm exec tsx scripts/migrate-boss-rewards.ts
```

Перенос с обязательной JSON-копией всех боссов до первой записи (указать новый путь вне Git-репозитория; родительская папка должна существовать):

```powershell
pnpm exec tsx scripts/migrate-boss-rewards.ts --apply --backup C:/Backups/evil-bosses-before-rewards.json
```

Скрипт не перезаписывает существующий backup. Он читает всех боссов без ограничения первой страницей и сохраняет только документы с прежними ссылками через Local API с обоснованным overrideAccess: true. Каждая запись переносится атомарно; результат проверяется по ID и количеству. При ошибке скрипт останавливается, старые колонки остаются. Уже перенесённые записи пропускаются при повторном запуске. JSON-копия боссов дополняет полноценную копию PostgreSQL, не заменяя её. Скрипт использует актуальный документ при сохранении, но параллельное редактирование на время backfill следует исключить.

Массовый перенос и schema push в рамках реализации агентом не запускались. Старые колонки удалять только отдельным этапом после резервного копирования, успешного переноса всех записей и проверки отсутствия ненулевых старых ссылок. До этого сохранять совместимость и защиту удаления по старым ссылкам.

## Проверки

Изолированные проверки хуков находятся в `tests/int/bossRewards.int.spec.ts` и `tests/int/questBossRewards.int.spec.ts`. Они не доказывают работу PostgreSQL и Payload.

`tests/int/bossRewardsPayload.int.spec.ts` проверяет сохранение richText через Payload, больше двух наград, валидацию количеств/дублей, запрет удаления, чтение старых ссылок, PATCH-перенос и повторное сохранение. Он запускается только при явном EVIL_TEST_DATABASE_URL, отличном от DATABASE_URL, с именем базы, заканчивающимся на `_test`. Только в этой выделенной базе тест создаёт и удаляет фикстуры; обычное подключение из .env не используется как fallback. Создание legacy-фикстуры выполняется адаптером Payload, бизнес-проверки — через Local API. Без выделенной базы тест пропускается.

В локальной админке проверить:

- обе новые подписи справочников и необязательное форматируемое описание обычного ресурса;
- старого босса до сохранения и после повторного открытия: оба прежних предмета имеют количество 1, остальные поля и ссылки сохранены;
- добавление третьей и последующих наград, default количества 1, отсутствие ограничений двумя строками;
- ошибки при повторе предмета, дробном/нулевом/отрицательном количестве и удалении используемого предмета;
- сохранение пустого списка, повторное сохранение и отсутствие возврата прежних наград;
- сохранение монет, названия, slug, изображения и ручного порядка.

Актуальный результат: проверка переноса старых наград боссов через Payload/PostgreSQL на временных фикстурах прошла, полный test:int — 89 успешных тестов. Общая модель проверена отдельно (24 обычных успешных сценария и ожидаемые падения из-за штатной join-пагинации). TypeScript и lint прошли; у lint пять прежних предупреждений. Schema push выполнялся только в выделенной тестовой базе; рабочий массовый backfill не запускался.

## Статус итоговой проверки

Пользователь подтвердил ручную проверку основных коллекций. Физическое завершение массового backfill и отсутствие старых ссылок этим не подтверждены; legacy-колонки остаются. Проверка PostgreSQL использует общий защищённый адаптер без замены DATABASE_URL; настройка и текущие ограничения описаны в [model-verification.md](model-verification.md).

Итоговое дополнение: после настройки выделенной базы проверка переноса старых ссылок боссов через Payload/PostgreSQL успешно выполнена, включая повторное сохранение и отсутствие дублей. Это проверка временных фикстур тестовой базы; массовый backfill рабочих боссов не выполнялся. Актуальный отчёт — [model-verification.md](model-verification.md).

Уточнение native join: сет из семи вещей полностью возвращается при текущем defaultLimit = 10. Для больших наборов стандартные списки с фильтром по equipmentSet/category используют прямые запросы; не следует автоматически считать их затронутыми дефектом native join. Минимальное воспроизведение, проверенный серверный findEvents и ограничения обходов: [model-verification.md](model-verification.md).
