# Evil — модель данных и админка

## Область текущего этапа

Реализация этапа ordinary-items/resources, режим PostgreSQL и порядок проверок описаны в [payload-development.md](payload-development.md).

Создать коллекции, поля, связи и удобные формы стандартной админки Payload. Пользователь затем заполняет тестовые игровые данные самостоятельно. Фронтенд и публичные страницы — отдельный этап.

Основа: Payload 3.92.1, Next.js 16.3.3, PostgreSQL, Lexical, Users и Media. Версии отражают проверенную исходную конфигурацию, не являются указанием на обновление.

Один игровой сервер. Исходное расписание — фиксированное UTC+3 без сезонного перевода. Монеты — общая валюта, хранится числом; отдельная коллекция валют не нужна.

## Коллекции

Существующие `users` и `media` сохранить. Предлагаемые slug ниже закрепляют технический словарь модели.

| Slug | Подпись | Назначение |
|---|---|---|
| resources | Кастомные ресурсы | Сердца, краски, жемчужины, ремкомплекты и другие ингредиенты |
| ordinary-items | Обычные предметы | Справочник обычных игровых ингредиентов, например мяса |
| equipment-sets | Сеты | Именованные комплекты одежды |
| clothing | Одежда | Части сетов и самостоятельные хазматы |
| weapons | Оружие | Конечные результаты крафта |
| event-times | Время запусков | Справочник времени суток по серверу |
| events | Ивенты | Активности по расписанию |
| quests | Квесты | Независимые активности без расписания |
| bosses | Ивент-боссы | Боссы без точного расписания |

Craft — будущий раздел сайта, а не отдельная коллекция. Он объединяет записи resources, clothing, weapons, у которых включён крафт. Сеты не крафтятся как отдельный предмет.

## Общие поля

У ресурсов, оружия, одежды, сетов и боссов: название, уникальный slug внутри коллекции, изображение через Media, описание Lexical. У ивентов: название, slug, короткое текстовое описание и полное описание Lexical. У квестов: название, slug и описание Lexical.

Название и slug обязательны. На первом этапе изображение и описание допускается заполнить позже. Генерацию slug делать стандартными средствами установленной версии Payload с возможностью ручного изменения. Это технические решения для удобства наполнения, а не игровые ограничения.

Характеристики предметов и назначения сетов описываются текстом. Никаких отдельных характеристик и уровней: уровней нет ни у сетов, ни у сердец, ни у оружия, ни у хазматов.

## Рецепты

Рецепт хранится внутри результата, отдельная коллекция рецептов не нужна. У одного результата ровно один рецепт.

Для resources, clothing и weapons:
- флаг «Можно скрафтить»;
- группа рецепта, доступная при включённом флаге;
- список кастомных ингредиентов: relationship на resources + целое положительное количество;
- список обычных ингредиентов: relationship на ordinary-items + целое положительное количество;
- стоимость в монетах: целое неотрицательное число, ноль означает бесплатно.

Если крафт включён, требуется хотя бы один ингредиент. Один ингредиент не повторяется в пределах соответствующего списка. Для ресурсов запретить прямую и косвенную циклическую зависимость рецептов; проверять связи по ID, без бесконечного populated-depth.

Обычные предметы имеют обязательные название и уникальный внутри коллекции технический slug, а также необязательную картинку; recipe и игровые источники им не нужны.

При выключении `craftable` рецепт сохраняется как неактивный. Его связи не участвуют в графе циклов, но продолжают запрещать удаление ингредиентов. Сохранённые строки, в том числе неактивные, должны содержать существующий ингредиент и положительное целое количество без повторов; стоимость, если задана, — целая неотрицательная. Для активного рецепта стоимость обязательна (по умолчанию 0).

Ресурс может крафтиться из других ресурсов и обычных предметов. Одежда и оружие являются конечными результатами и не предлагаются в ингредиентах.

Не фиксировать приблизительные количества из разговора в качестве игровых данных.

## Сеты и одежда

Сет имеет название, картинку и описание, но не уровень и не собственный рецепт.

В clothing предусмотреть вид: часть сета или хазмат. Для части сета — обязательная связь с одним equipment-sets; для хазмата связь с сетом отсутствует. Часть одежды создаётся один раз. Обратный состав сета получать по этой связи, не хранить второй редактируемый список.

У каждого сета свои части. Не ограничивать состав четырьмя предметами: пример Evil включает шлем, нагрудник, килт, толстовку, штаны, ботинки и перчатки. Не требовать ровно семь для всех сетов.

Хазматы самостоятельные, с разными описаниями и рецептами. Все характеристики вводятся в описание.

## Расписание ивентов

event-times содержит уникальное время суток в UTC+3. Для понятного ввода использовать HH:mm; для надёжного сравнения предусмотреть число минут от начала суток (0–1439), вычисляемое из времени и недоступное для независимого ручного редактирования. Не использовать произвольную дату или часовой пояс машины для хранения ежедневного времени.

В events — relationship hasMany на event-times. Одна запись времени может использоваться несколькими ивентами. Не дублировать выбранное расписание отдельными текстовыми полями.

Времена выбираются вручную. Несмотря на повторение ивентов раз в три часа, автоматическую генерацию не делать: пользователь выбирает известные реальные времена из справочника. Расписание ежедневно одинаковое. Точное время рестарта не согласовано и не должно быть выдумано.

## Ивенты и награды

events:
- общие поля ивента;
- времена запуска;
- монеты за прохождение — целое неотрицательное число;
- КД прохождения — целое неотрицательное число минут, подпись с единицей измерения;
- список возможных ресурсных наград: resource, minQuantity, maxQuantity.

Количество целое: 0 <= minQuantity <= maxQuantity, maxQuantity >= 1. У ресурса с minQuantity = 0 получение не гарантировано. Не вводить шансы и группы случайного выбора. Одинаковый ресурс не повторять в списке наград.

КД — информация о правилах игры, не интервал запуска. Личные отметки «прошёл», таймеры и аккаунты посетителей исключены.

Проверенный пример: «Паромный терминал», кратко «Освободить заложников», полное описание «На паромный терминал привезут заложников, которых вам нужно освободить». Награда 440 монет, деревянное сердце 0–2, КД 360 минут. Первый запуск 05:25, далее раз в 3 часа; полный список времён заполнит пользователь. Пример не создавать автоматически.

## Квесты

quests — прежние «задания», без расписания и без связей с ивентами или боссами.

Поля: название, slug, описание, монеты, список возможных наград (resource + фиксированное целое положительное количество). У каждого квеста свой список. Не добавлять расписание, цепочки прохождения или требования принести предметы. КД квестов не согласован — не добавлять.

## Боссы

bosses: название, slug, картинка, описание; монеты при наличии (целое неотрицательное число).

Две связи на resources: золотое сердце и персональное сердце. По одной штуке каждого, это фиксированное правило. Две ссылки должны вести на разные ресурсы. Золотое сердце — общая запись для разных боссов, а не копия на каждого босса. Не определять ресурс по изменяемому названию или жёстко заданному числовому ID. Способ обозначить общее золотое сердце определить при реализации и описать, не создавать его автоматически.

Точного расписания нет. Связь с events не подтверждена и не добавляется.

## Обратные связи

Источники получения ресурса определяются по наградам events, quests и bosses. Использование в крафте определяется по ингредиентам recipes в resources, clothing, weapons. Собственный рецепт ресурса хранится в нём самом.

Обратные связи выводятся запросами или подходящими join-полями Payload, если поддерживаются выбранные вложенные пути. Не обещать join без проверки установленной версии и не хранить ручные дубликаты.

## Будущий фильтр ивентов — требования к модели

Сам UI фильтра и публичные страницы сейчас не реализуются. До завершения модели проверить запросами Payload на отдельной тестовой базе:
- без условий доступны все ивенты;
- диапазон времени включителен с обеих сторон;
- хотя бы один запуск ивента должен попадать в диапазон;
- поддерживается переход через полночь, например 23:00–02:00;
- при выборе нескольких ресурсов нужны ВСЕ выбранные ресурсы в возможных наградах;
- отсутствие гарантии выпадения не исключает ресурс из фильтра;
- монеты от и до, включительно, любую границу можно пропустить;
- все заданные группы условий объединяются через AND;
- возвращаются все подходящие ивенты, один документ на ивент, без произвольного ограничения; учитывать пагинацию.

Пример диапазона 08:00–10:00 включает запуск 09:55. На будущем фронтенде показывать все подходящие запуски каждого найденного ивента.

Особенно проверить запросы hasMany и ресурсов во вложенном массиве на PostgreSQL. Не считать правильность сложного запроса доказанной по одному конфигу.

Будущий выбор часового пояса меняет отображение и интерпретацию диапазона посетителя; база хранит UTC+3. Учитывать календарную дату для зон с сезонным переводом. Поведение диапазона с одинаковыми началом и концом и значение часового пояса по умолчанию окончательно уточнить перед фронтендом (ранее предложен UTC+3).

## Целостность и доступ

Количество ингредиентов и фиксированных наград — положительные целые. Монеты и КД — неотрицательные целые. Проверять на сервере, не только admin.condition.

Перед удалением записи, используемой в рецепте, наградах, расписании или составе сета, показывать понятную ошибку и требовать сначала убрать ссылки. Не каскадно удалять связанные игровые сущности.

Не изменять auth Users и не добавлять роли без отдельной задачи. Изменения данных только аутентифицированными пользователями. Схему публичного чтения согласовать при реализации фронтенда.

## Этапы реализации

1. Документация и правила.
2. Ordinary-items и resources с рецептами.
3. Equipment-sets, clothing, weapons; общее определение полей recipe по фактическому повторению.
4. Event-times, events, quests, bosses.
5. Проверки связей, валидации и фильтров через API; ручная проверка админки.
6. Пользователь заполняет данные. После этого отдельная задача на фронтенд.

Использовать существующие Media и Users. Генерировать типы после изменения схемы. Выбрать и задокументировать режим изменения схемы PostgreSQL; не сбрасывать локальную базу и не применять тесты с записью к ней.

## Открытые детали

- Точное время рестарта не подтверждено; автоматическое построение расписания не требуется.
- Назначение Evil пользователь ещё не указал, не придумывать.
- Политика публичного чтения, правила одинаковых границ времени и окончательный UI часовых поясов — последующий этап.
- Все рецепты сердец и полный игровой каталог пользователь заполнит самостоятельно.
