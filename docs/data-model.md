# Evil — модель данных и админка

## Область текущего этапа

Реализация игровых коллекций, режим PostgreSQL и порядок проверок описаны в [payload-development.md](payload-development.md). Квесты и боссы: [quests-bosses-development.md](quests-bosses-development.md).

Основные коллекции, поля, связи и формы стандартной админки Payload созданы; пользователь подтвердил ручную проверку. Текущий этап — итоговая проверка модели и изолированные интеграционные тесты, без новых полей. Игровой каталог пользователь заполняет самостоятельно. Фронтенд и публичные страницы — отдельный этап. Статус автоматических проверок и настройка тестовой базы: [model-verification.md](model-verification.md).

Основа: Payload 3.92.1, Next.js 16.3.3, PostgreSQL, Lexical, Users и Media. Версии отражают проверенную исходную конфигурацию, не являются указанием на обновление.

Один игровой сервер. Исходное расписание — фиксированное UTC+3 без сезонного перевода. Монеты — общая валюта, хранится числом; отдельная коллекция валют не нужна.

## Коллекции

Существующие `users` и `media` сохранены. Slug ниже закрепляют технический словарь реализованной модели.

| Slug | Подпись | Назначение |
|---|---|---|
| resources | Кастомные предметы | Сердца, краски, жемчужины, ремкомплекты и другие ингредиенты |
| ordinary-items | Обычные ресурсы | Справочник обычных игровых ингредиентов, например мяса |
| equipment-sets | Сеты | Именованные комплекты одежды |
| clothing | Одежда | Части сетов и самостоятельные хазматы |
| weapons | Оружие | Конечные результаты крафта |
| event-times | Время запусков | Справочник времени суток по серверу |
| events | Ивенты | Активности по расписанию |
| quests | Квесты | Независимые активности без расписания |
| quest-categories | Категории квестов | Справочник категорий для одной необязательной связи квеста |
| bosses | Ивент-боссы | Боссы без точного расписания |

Craft — будущий раздел сайта, а не отдельная коллекция. Он объединяет записи resources, clothing, weapons, у которых включён крафт. Сеты не крафтятся как отдельный предмет.

Все игровые коллекции должны поддерживать ручной порядок записей штатным `orderable: true` Payload. Это относится к уже созданным ordinary-items, resources, equipment-sets, clothing, weapons и ко всем будущим игровым коллекциям. Users и Media не меняются. Порядок сохраняется в служебном поле `_order`; будущий вывод на сайт использует сортировку запросов `sort: '_order'` с учётом пагинации. Собственных компонентов перетаскивания и отдельных полей порядка не создавать.

## Общие поля

У обычных ресурсов, кастомных предметов, оружия, одежды, сетов и боссов: название, уникальный slug внутри коллекции, изображение через Media, описание Lexical. У ивентов: название, slug, короткое текстовое описание и полное описание Lexical. У квестов: название, slug и описание Lexical.

Название и slug обязательны. На первом этапе изображение и описание допускается заполнить позже. Генерацию slug делать стандартными средствами установленной версии Payload с возможностью ручного изменения. Это технические решения для удобства наполнения, а не игровые ограничения.

Общий механизм `itemSlug` автоматически обновляет slug из названия новой записи до ручного редактирования. Русские буквы транслитерируются в латиницу, регистр нижний, разделитель — одиночный дефис: «Шлем Evil» → `shlem-evil`. Unlock открывает ручное редактирование. Непустой slug сохранённой записи не меняется при переименовании; существующие slug не нормализуются массово. При создании через API пустой или отсутствующий slug генерируется на сервере до required-валидации. Уникальность внутри коллекции сохраняется.

Характеристики предметов и назначения сетов описываются текстом. Никаких отдельных характеристик и уровней: уровней нет ни у сетов, ни у сердец, ни у оружия, ни у хазматов.

## Рецепты

Рецепт хранится внутри результата, отдельная коллекция рецептов не нужна. У одного результата ровно один рецепт.

Для resources, clothing и weapons:
- флаг «Можно скрафтить»;
- группа рецепта, доступная при включённом флаге;
- список кастомных ингредиентов: relationship на resources + целое положительное количество;
- список обычных ингредиентов: relationship на ordinary-items + целое положительное количество;
- стоимость в монетах: целое неотрицательное число, ноль означает бесплатно.

Если крафт включён, требуется хотя бы один ингредиент. Один ингредиент не повторяется в пределах соответствующего списка. Для ресурсов запретить прямую и косвенную циклическую зависимость рецептов; проверять связи по ID, без бесконечного populated-depth.

Обычные ресурсы имеют обязательные название и уникальный внутри коллекции технический slug, а также необязательные картинку и описание richText с глобальным Lexical; собственного recipe и вручную редактируемого списка источников им не нужно. Использование в наградах квестов определяется по `quests.ordinaryRewards.item`.

При выключении `craftable` рецепт сохраняется как неактивный. Его связи не участвуют в графе циклов, но продолжают запрещать удаление ингредиентов. Сохранённые строки, в том числе неактивные, должны содержать существующий ингредиент и положительное целое количество без повторов; стоимость, если задана, — целая неотрицательная. Для активного рецепта стоимость обязательна (по умолчанию 0).

Кастомный предмет может крафтиться из других кастомных предметов и обычных ресурсов. Одежда и оружие являются конечными результатами и не предлагаются в ингредиентах.

Не фиксировать приблизительные количества из разговора в качестве игровых данных.

## Сеты и одежда

Сет имеет название, картинку и описание, но не уровень и не собственный рецепт.

В clothing принадлежность определяется единственной необязательной связью `equipmentSet` с одним equipment-sets: заполнена — часть выбранного сета, пустая — самостоятельный хазмат. Отдельного поля вида одежды нет. Часть одежды создаётся один раз. Обратный состав сета получать по этой связи, не хранить второй редактируемый список.

Реализация: `clothing.equipmentSet` допускает отсутствие значения; если сет выбран, его существование проверяется на сервере, в том числе при частичных обновлениях. Пояснение поля: «Для части комплекта выберите сет. Для хазмата оставьте пустым». В `equipment-sets.parts` используется штатное join-поле Payload по `equipmentSet`, без второго списка и ограничения числа частей. Удаление используемого сета запрещено.

Поля `craftable` и `recipe` общие для resources, clothing и weapons; структура существующих рецептов ресурсов сохранена. Запрет удаления resources и ordinary-items проверяет активные и неактивные рецепты всех трёх коллекций. Одежда и оружие не входят в допустимые коллекции ингредиентов. Защита удаления Media отложена.

У каждого сета свои части. Не ограничивать состав четырьмя предметами: пример Evil включает шлем, нагрудник, килт, толстовку, штаны, ботинки и перчатки. Не требовать ровно семь для всех сетов.

Хазматы самостоятельные, с разными описаниями и рецептами. Все характеристики вводятся в описание.

## Расписание ивентов

event-times содержит уникальное время суток в UTC+3. Для понятного ввода использовать HH:mm; для надёжного сравнения предусмотреть число минут от начала суток (0–1439), вычисляемое из времени и недоступное для независимого ручного редактирования. Не использовать произвольную дату или часовой пояс машины для хранения ежедневного времени.

В events — relationship hasMany на event-times. Одна запись времени может использоваться несколькими ивентами. Не дублировать выбранное расписание отдельными текстовыми полями.

Технические поля event-times: `time` — обязательная уникальная строка строго HH:mm, она же название записи в выборе; `minutes` — обязательное индексируемое число 0–1439, вычисляемое сервером перед валидацией при каждом сохранении. В админке minutes доступно только для чтения; переданное через API значение заменяется вычисленным. Хронологическая сортировка запросов — `sort: 'minutes'`, ручной порядок — `_order`; эти порядки независимы. Удаление времени, выбранного в `events.launchTimes`, запрещено до снятия ссылок.

Времена выбираются вручную. Несмотря на повторение ивентов раз в три часа, автоматическую генерацию не делать: пользователь выбирает известные реальные времена из справочника. Расписание ежедневно одинаковое. Точное время рестарта не согласовано и не должно быть выдумано.

## Ивенты и награды

events:
- общие поля ивента;
- времена запуска;
- монеты за прохождение — целое неотрицательное число;
- КД прохождения — целое неотрицательное число минут, подпись с единицей измерения;
- список возможных ресурсных наград: resource, minQuantity, maxQuantity.

Количество целое: 0 <= minQuantity <= maxQuantity, maxQuantity >= 1. У ресурса с minQuantity = 0 получение не гарантировано. Не вводить шансы и группы случайного выбора. Одинаковый ресурс не повторять в списке наград.

Реализованные поля events: `name`, `slug`, `shortDescription` (text), `description` (richText с общим Lexical), `launchTimes` (hasMany relationship), `coins`, `cooldownMinutes`, `rewards` (массив resource + minQuantity + maxQuantity). Монеты и КД обязательны, по умолчанию 0. Описания, список времён и награды можно заполнить позже. Дубли времён запрещены; награды и расписание проверяются на существование выбранных документов. Числа проверяются как безопасные целые JavaScript. Частичные обновления проверяются с учётом прежних данных; переданный массив заменяет прежний целиком. Ресурс из возможных наград, включая minQuantity = 0, нельзя удалить до снятия ссылки.

КД — информация о правилах игры, не интервал запуска. Личные отметки «прошёл», таймеры и аккаунты посетителей исключены.

Проверенный пример: «Паромный терминал», кратко «Освободить заложников», полное описание «На паромный терминал привезут заложников, которых вам нужно освободить». Награда 440 монет, деревянное сердце 0–2, КД 360 минут. Первый запуск 05:25, далее раз в 3 часа; полный список времён заполнит пользователь. Пример не создавать автоматически.

## Квесты

quests — прежние «задания», без расписания и без связей с ивентами или боссами.

Поля квеста: название, slug, описание, монеты, необязательный текстовый КД, необязательное необходимое количество, категория и отдельные списки ресурсных и обычных наград. КД — свободная справочная строка, например «6 часов» или «Раз в сутки», без персональных таймеров. Расписание, цепочки прохождения и другие игровые механики не добавляются.

Реализация quests: `name`, `slug`, `description` (Lexical), `coins` (безопасное целое ≥ 0), необязательные `cooldown` (text), `requiredQuantity` (положительное безопасное целое без defaultValue), `category` (одна quest-categories), существующие `rewards` (resource + quantity) и `ordinaryRewards` (item + quantity). «Необходимое количество» — сколько нужно собрать, добыть или выполнить для завершения квеста, а не награда. Пустое значение не означает 0. В каждом списке наград отдельно запрещены дубли по ID; ссылки должны существовать, количества — положительные безопасные целые. PATCH учитывает сохранённые данные, массивы заменяются независимо. Сохранение старого списка rewards не требует преобразования.

Quest-categories: обязательные name и уникальный slug с общей транслитерацией, ручной порядок и доступ Users. Единственная сохраняемая связь — `quests.category`. В категории `quests` — штатное join-поле по этой связи, с пагинацией и сортировкой `_order`; второго редактируемого списка нет. Используемые категории и обычные ресурсы из наград защищены от удаления. Переход числового КД квестов в текст выполняется без удаления старой колонки: см. [quests-bosses-development.md](quests-bosses-development.md). КД ивентов остаётся числом минут.

## Боссы

bosses: название, slug, картинка, описание; монеты — обязательное безопасное целое неотрицательное число, по умолчанию 0. Картинку и описание можно заполнить позже.

Награды — стандартный массив Payload `rewards` с кнопкой добавления строк, без ограничения двумя предметами. Каждая строка: обязательный `resource` → resources («Кастомный предмет») и обязательное положительное безопасное целое `quantity`, по умолчанию 1. Один предмет не повторяется в массиве; выбранные документы должны существовать. Список можно заполнить позже или очистить; монеты хранятся отдельно. PATCH без rewards сохраняет награды, переданный массив заменяет прежний целиком.

Прежние `goldenHeart` и `personalHeart` больше не являются игровой моделью или обязательными полями: временно сохранены скрытыми и необязательными для безопасного переноса при development schema push. Ссылки отображаются в rewards с количеством 1; при сохранении переносятся атомарно, без повторов по ID, с сохранением уже заданных количеств. Отдельный массовый перенос и условия удаления колонок описаны в [boss-rewards-transition.md](boss-rewards-transition.md).

Удаление resources блокируется при использовании в `bosses.rewards.resource`, наградах quests/events и рецептах. До завершения переноса также учитываются старые ссылки боссов. Сначала нужно убрать ссылку из наград или удалить босса; каскадного удаления нет. Quests и bosses сохраняют штатный ручной порядок; чтение публичное, запись и удаление доступны только Users.

Точного расписания нет. Связь с events не подтверждена и не добавляется.

## Обратные связи

Источники получения ресурса определяются по наградам events, quests и bosses. Использование в крафте определяется по ингредиентам recipes в resources, clothing, weapons. Собственный рецепт ресурса хранится в нём самом.

Обратные связи выводятся запросами или подходящими join-полями Payload, если поддерживаются выбранные вложенные пути. Не обещать join без проверки установленной версии и не хранить ручные дубликаты.

## Будущий фильтр ивентов — требования к модели

Сам UI фильтра и публичные страницы сейчас не реализуются. До завершения модели проверить запросами Payload на отдельной тестовой базе:
- без условий доступны все ивенты;
- диапазон времени включителен с обеих сторон;
- хотя бы один запуск ивента должен попадать в диапазон;
- поддерживается переход через полночь, например 23:00–02:00;
- при выборе нескольких кастомных предметов нужны ВСЕ выбранные предметы в возможных наградах;
- отсутствие гарантии выпадения не исключает кастомный предмет из фильтра;
- монеты от и до, включительно, любую границу можно пропустить;
- все заданные группы условий объединяются через AND;
- возвращаются все подходящие ивенты, один документ на ивент, без произвольного ограничения; учитывать пагинацию.

Пример диапазона 08:00–10:00 включает запуск 09:55. На будущем фронтенде показывать все подходящие запуски каждого найденного ивента.

Совместный фильтр проверен через Payload/PostgreSQL на выделенной тестовой базе. Для ВСЕХ предметов используются отдельные запросы по каждому предмету с пересечением ID и полной пагинацией; несколько equals по одному пути массива в одном AND на адаптере 3.92.1 неверны. Прямые обратные запросы проверены; штатная пагинация join на третьей странице имеет известный дефект. См. [model-verification.md](model-verification.md).

Будущий выбор часового пояса меняет отображение и интерпретацию диапазона посетителя; база хранит UTC+3. Учитывать календарную дату для зон с сезонным переводом. Поведение диапазона с одинаковыми началом и концом и значение часового пояса по умолчанию окончательно уточнить перед фронтендом (ранее предложен UTC+3).

## Целостность и доступ

Количество ингредиентов, фиксированных наград и заполненное requiredQuantity квеста — положительные целые. Монеты и КД ивентов — неотрицательные целые; КД квеста — необязательный текст. Проверять на сервере, не только admin.condition.

Перед удалением записи, используемой в рецепте, наградах, расписании или составе сета, показывать понятную ошибку и требовать сначала убрать ссылки. Не каскадно удалять связанные игровые сущности.

Не изменять auth Users и не добавлять роли без отдельной задачи. Изменения данных только аутентифицированными пользователями. Публичное чтение согласовано для homepage и семи коллекций каталога ниже; остальные справочники требуют отдельного задания.

## Этапы реализации

1. Документация и правила.
2. Ordinary-items и resources с рецептами.
3. Equipment-sets, clothing, weapons; общее определение полей recipe по фактическому повторению.
4. Event-times, events, quests, bosses.
5. Проверки связей, валидации и фильтров через API; ручная проверка админки.
6. Пользователь заполняет данные. После этого отдельная задача на фронтенд.

Использовать существующие Media и Users. Генерировать типы после изменения схемы. Выбрать и задокументировать режим изменения схемы PostgreSQL; не сбрасывать локальную базу и не применять тесты с записью к ней.

## Открытые детали

- Точное время рестарта не подтверждено; автоматическое построение расписания не требуется.
- Назначение Evil пользователь ещё не указал, не придумывать.
- Публичное чтение семи коллекций согласовано на этапе каталога (ниже); правила одинаковых границ времени и окончательный UI часовых поясов — последующий этап.
- Все рецепты сердец и полный игровой каталог пользователь заполнит самостоятельно.


## Global главной страницы

Публичная главная использует единственный Global homepage («Главная страница»): title — обязательное название с default EvilIsland; description — необязательный richText с глобальным Lexical; image — необязательная загрузка из Media. Чтение явно публичное, изменение только аутентифицированным Users. Это не изменение прав игровых коллекций или Users. Блоков, новостей и Telegram нет. Страница читает Global серверным Local API с overrideAccess: false на каждый запрос (force-dynamic), выводит Lexical официальным React-рендерером и не подменяет ошибки пустым контентом. Подробности схемы, тестов и ручной проверки — в frontend-plan.md, раздел «Второй этап».

## Публичный каталог кастомных предметов

На этапе resources явно разрешено публичное чтение resources, ordinary-items, events, quests, bosses, clothing и weapons. Create/update/delete остаются только Users, Users публично не открывается. Quest-categories открывается для публичного чтения на этапе квестов; event-times открыта для публичного чтения на этапе ивентов; equipment-sets открыта на этапе страниц одежды. Публичные ответы не содержат неактивного recipe; Users и внутренние доверенные операции сохраняют доступ к нему. Схема recipe и запреты удаления не меняются.

Канонические страницы — /items (каталог), /items/[slug] и /ordinary-resources/[slug]. Без дополнительных страниц других разделов. Порядок `_order` сохранён. Для источников и использования в активных рецептах применяются прямые запросы, depth 0, узкие проекции, все страницы и пакетное разрешение ингредиентов/изображений. Детали, проверки и ограничения — в frontend-plan.md, третий этап.

Этап страниц одежды/оружия: /clothing/[slug] и /weapons/[slug] показывают активный рецепт общим компонентом. Equipment-sets также открыта для публичного чтения названия связанного сета; запись и удаление остаются только Users. Страница сета /clothing/sets/[slug] добавлена пятым этапом, состав читается прямым обратным запросом clothing.equipmentSet с полной пагинацией. Каталог /clothing разделён на сеты и хазматы, /weapons показывает все weapons. Подробности в четвёртом и пятом этапах frontend-plan.md.

Публичный /craft объединяет только craftable=true из resources/clothing/weapons (включая части сетов и хазматы), без equipment-sets. Порядок: resources → clothing → weapons, внутри _order,id; карточки ведут на канонические детали. Модель и рецепты не меняются. Подробности в шестом этапе frontend-plan.md.

Публичные bosses: /bosses и /bosses/[slug], карточки/детали показывают coins и rewards с количеством и ссылками на resources. Источники bosses на resources ссылаются обратно. Используется существующий rewards API и модельный слой совместимости; схема и данные не менялись. Подробности в седьмом этапе frontend-plan.md.

Ивенты: /events и /events/[slug], SSR и фильтрация через findEvents (монеты включительно + ВСЕ предметы), времена запуска UTC+3 в детали. Event-times читается публично, запись только Users. Поля и игровые правила не меняются. Детали, компоненты и ограничения — восьмой этап frontend-plan.md.

Публичные квесты: /quests и /quests/[slug], SSR-каталог с категорией, монетами и ALL-наградами обоих типов через пересечение ID. Quest-categories открыта для чтения, запись только Users; схемы квестов и категорий не менялись. Подробности и ручная проверка — девятый этап frontend-plan.md.

Расписание /event-launches строит реальные экземпляры запусков из неизменённых HH:mm UTC+3; общий выбор IANA-зоны применяется также в детали ивента. Поля/права/данные не менялись. Правила ближайшего диапазона, DST и ограничения описаны в десятом этапе frontend-plan.md.
