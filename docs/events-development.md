# Event-times и events: реализация и проверка

## Область этапа

Этот документ описывает event-times и events в составе уже созданной общей модели. Доступ — только аутентифицированным Users, включая чтение. В обеих коллекциях включён штатный `orderable: true`; ручной порядок хранится в `_order`. Подключение PostgreSQL и development schema push сохранены, миграции и игровые записи не добавлялись. Общие коллекции и квесты/боссы описаны в data-model.md; фронтенд и публичный фильтр не реализованы.

## Поля и серверные правила

Event-times: обязательное уникальное `time` строго HH:mm от 00:00 до 23:59 (UTC+3), без даты и зависимости от часового пояса машины. Оно используется как название записи в relationship. `minutes` индексируется, показывается только для чтения и каждый раз вычисляется в beforeValidate: часы × 60 + минуты. До первого сохранения стандартный input показывает 0, чтобы его required-валидация не блокировала отправку формы с недоступным для редактирования полем. При сохранении сервер всегда заменяет значение вычисленным. Значение из API также игнорируется в пользу вычисленного, в том числе при PATCH только minutes или служебного `_order`. Запрос с `sort: 'minutes'` возвращает хронологический порядок независимо от перетаскивания в админке.

Events: обязательные `name` и уникальный `slug` через существующий общий механизм транслитерации. `shortDescription` — обычный text, `description` — richText с общим Lexical (абзацы, заголовки, жирный/курсив, списки, ссылки). `launchTimes` — вручную выбираемая hasMany-связь с event-times без повторов. `coins` и `cooldownMinutes` — обязательные безопасные целые ≥ 0, по умолчанию 0. КД — правило прохождения в минутах, не интервал запусков и не личный таймер.

`rewards` содержит `resource`, `minQuantity`, `maxQuantity`; ресурс должен существовать, не повторяться; количества безопасные целые, 0 ≤ минимум ≤ максимум и максимум ≥ 1. Минимум 0 не исключает ресурс из возможных наград. Расписание и список наград могут быть пустыми при первоначальном наполнении. Числа и ссылки проверяются сервером при создании и частичном обновлении; массив заменяется целиком. Шансы, группы случайного выбора, автоповторы, личные отметки и таймеры отсутствуют.

Удаление выбранного времени блокируется запросом по `events.launchTimes`. Защита resources дополнена проверкой `events.rewards.resource`, включая негарантированные награды. Прежние проверки рецептов и сетов сохранены; каскадного удаления нет. Вложенные запросы передают `req` для текущей транзакции. Существующие ограничения гонок между созданием ссылки и удалением сохраняются: дополнительных блокировок и SQL-триггеров нет.

## Будущий совместный фильтр

UI фильтра и отдельный публичный endpoint в этом этапе не создаются. Схема предоставляет числовые минуты, hasMany-расписание, массив возможных ресурсов и числовые монеты.

Алгоритм выделен в минимальную серверную функцию findEvents в src/queries/findEvents.ts; существующие интеграционные сценарии вызывают её напрямую. Он проверен на отдельной PostgreSQL-базе:

1. Преобразовать границы HH:mm в минуты сервера UTC+3. Для обычного диапазона выбрать event-times с `minutes >= начало AND minutes <= конец`. Для перехода через полночь — `minutes >= начало OR minutes <= конец`. Границы включены. Собирать все ID времён с учётом пагинации, например с `sort: 'minutes'`.
2. Если есть ограничение времени, искать events с `launchTimes: { in: найденныеID }`. Если времён не найдено — результат пустой; нельзя просто опустить условие. При отсутствии диапазона времени условие launchTimes не добавляется, доступны также ивенты с пустым расписанием. Двухшаговый поиск не смешивает нижнюю и верхнюю границы разных запусков одного ивента.
3. Для каждого выбранного кастомного предмета выполнить отдельный запрос events по `{ 'rewards.resource': { equals: ID } }`, собрать все страницы и пересечь ID ивентов. Итоговый запрос ограничить этим пересечением. Несколько equals по этому вложенному пути в одном AND на установленном PostgreSQL-адаптере дают пустой результат для разных предметов, поскольку связываются с одной строкой массива. Один in означает ЛЮБОЙ предмет и также не соответствует ВСЕ. По minQuantity не фильтровать.
4. В тот же AND добавить `coins >= от` и `coins <= до`; любую границу можно пропустить. Явно учитывать 0, а не проверять границу на truthy.
5. Запросить все страницы events, например с `sort: '_order'`; один документ на ивент. Без условий не добавлять ограничений. Будущий вывод подходящих запусков выполняется по выбранным временам, а не только по первому запуску.

Одинаковые начало и конец диапазона и часовой пояс посетителя по-прежнему требуют согласования перед фронтендом. Алгоритм не реализует перевод часовых поясов. Поведение hasMany и пересечения ID подтверждено тестами через Payload/PostgreSQL; неверный вариант нескольких AND по одному пути массива заменён. Для согласованного снимка двух шагов следует передавать один req с транзакцией; серверная функция принимает req и обязательный overrideAccess, но не создаёт HTTP-маршрутов или интерфейса.

## Что проверять на отдельной тестовой базе

Выделенная тестовая PostgreSQL-база подключена; проверки через Payload выполнены. Итог и известный дефект join-пагинации — в [model-verification.md](model-verification.md). Подготовлены проверки совместного фильтра, обратных запросов, удаления и прав: [model-verification.md](model-verification.md). На рабочем подключении тесты не выполняются. Требования к проверкам через Payload, с `overrideAccess: false` для проверки прав:

- запрет доступа без Users и доступ с Users; уникальность time и slug;
- HH:mm: 00:00 → 0, 05:25 → 325, 23:59 → 1439; отклонение 24:00, 12:60, 5:25, секунд, дат, пробелов и переводов строки;
- PATCH времени пересчитывает minutes; попытка задать только minutes или несогласованную пару не меняет вычисленное соответствие;
- создание и PATCH events: нули монет/КД допустимы, дроби и отрицательные значения отклоняются; диапазоны наград 0–1, 1–1 допустимы, 0–0, отрицательные, дробные и минимум больше максимума отклоняются;
- отсутствующие ссылки, дубли ресурсов и времён; частичное изменение имени/монет не теряет расписание и награды;
- запрет удаления времени из одного или нескольких ивентов, ресурса из rewards (включая minQuantity = 0), а также регрессия запретов удаления ингредиентов из рецептов;
- после снятия всех ссылок удаление доступно, связанные игровые сущности не удаляются каскадно;
- сохранность ручного порядка обеих коллекций после перезагрузки, отдельная сортировка event-times по minutes;
- совместный фильтр: без условий все ивенты; 08:00–10:00 включает 09:55 и обе границы; ивент с запусками 07:00 и 11:00 не должен попасть в этот диапазон; 23:00–02:00 включает обе стороны полуночи; несколько ресурсов требуют все, в том числе с минимумом 0; монеты от/до включительно и с пропущенными границами; условия сочетаются AND; результаты больше одной страницы не теряются и не дублируются.

## Ручной сценарий админки

Пользователь вводит собственные проверочные записи; автоматического наполнения нет.

1. После development schema push открыть «Время запусков», ввести допустимое время, сохранить и проверить число минут. Проверить ошибочный формат и повтор времени. Поле minutes не должно редактироваться отдельно.
2. В «Ивентах» проверить автоматический slug из русского названия, обычное короткое описание и форматирование полного описания Lexical. Выбрать несколько времён из справочника; одно время можно использовать в разных ивентах.
3. Сохранить монеты и КД с нулём, затем проверить ошибки дробных/отрицательных значений. Добавить награду 0–1 и проверить отсутствие предупреждения об обязательном выпадении; проверить дубли, минимум больше максимума и максимум 0.
4. Повторно открыть ивент, изменить только название/монеты и убедиться в сохранности расписания и наград. Проверить сохранение ручного slug при переименовании.
5. Попытаться удалить выбранное время и наградной ресурс — должна появиться понятная ошибка. Снять ссылки и повторить; если ресурс ещё нужен в рецептах, прежний запрет должен сохраняться.
6. Переставить строки в обеих коллекциях, обновить страницу и проверить порядок. Отдельно отсортировать время по minutes и убедиться в хронологическом порядке.

Ручная проверка форм не заменяет проверки сложных запросов и прав через Payload/PostgreSQL. Пользователь подтвердил ручную проверку основных коллекций; автоматические SQL-проверки выполнены отдельно на тестовой базе; известное ограничение штатной join-пагинации описано в model-verification.md.

Итоговая проверка через тестовую PostgreSQL выполнена; прямые обратные запросы с пагинацией работают. Штатная пагинация join на третьей странице имеет подтверждённый дефект адаптера 3.92.1. Подробности, обход прямыми запросами и ожидаемые падения тестов: [model-verification.md](model-verification.md).

Уточнение native join: сет из семи вещей полностью возвращается при текущем defaultLimit = 10. Для больших наборов стандартные списки с фильтром по equipmentSet/category используют прямые запросы; не следует автоматически считать их затронутыми дефектом native join. Минимальное воспроизведение, проверенный серверный findEvents и ограничения обходов: [model-verification.md](model-verification.md).
