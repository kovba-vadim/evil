# Длительность и пригодность запусков

Этап напоминаний и «Я играю» зафиксирован отдельно: `ea095db`. Изменения этого этапа оставлены незакоммиченными. Посторонние изменения Media/import map/типов/проверок папок сохранены. GitHub, push, merge и развёртывание не использовались.

## Данные и правило

`events.durationMinutes` — обязательное положительное безопасное целое, default 30. В основной вкладке админки рядом с расписанием: «Длительность ивента, минут». Это расчётное время от запуска до окончания; ивент может закончиться раньше, если его прошли. Длительность не изменяет расписание или личный КД и не вычисляется из следующего запуска. Изменять её могут только Users с существующим правом редактирования events; Players и гости, включая прямой REST API, не могут.

**Прежнее правило «КД никогда не исключает запуск» заменено.** Общая функция `src/lib/launch-eligibility.ts` сравнивает точные UTC-моменты: без активного КД запуск подходит; с активным КД он подходит только при `cooldownUntil < launchAt + durationMinutes`. Равенство не подходит. Галочка отображения КД влияет только на текст. Форматирование использует существующий часовой пояс игрока; HH:mm расписания остаются фиксированными UTC+3.

Регулярные подписки пропускают неподходящие запуски. Предупреждение должно быть в будущем; предупреждение и начало должны входить в `[startedAt, endsAt)`. Конец ивента может выходить за период. При отсутствии подходящего запуска подписка сохраняется включённой с объяснением.

Новый once предлагает ближайший подходящий запуск и перед записью пересчитывает предложение; устаревшее отклоняется с 409 и требует явного подтверждения. Сохранённый once сохраняет исходные UTC-моменты при новом КД или изменении длительности: «Этот запуск не подходит по вашему КД», действие «Перевыбрать запуск», без предпросмотра готового сообщения. Отмена КД возвращает пригодность того же запуска, если предупреждение ещё в будущем. Прошедшее предупреждение не оживает. Изменение КД и сохранение напоминания используют общую транзакционную блокировку по игроку.

После успешной отметки/отмены КД интерфейс перечитывает напоминания. Также обновляет их при загрузке и возврате на вкладку. Изменение длительности администратором учитывается при следующем серверном чтении; push-канала между браузерами нет.

## Резервная копия и заполнение

Перед изменением схемы создан custom-архив:

`D:\Backups\Evil\evil-before-event-duration-20261114-223721.dump`

Размер 200571 байт; `pg_dump` завершился с кодом 0, `pg_restore --list` — с кодом 0 (531 запись TOC). Использованы установленные PostgreSQL 18 utilities и подключение проекта без вывода пароля/URL. Рядом сохранён снимок строк events и связанных events_* для сравнения.

До изменения в рабочей базе было 14 ивентов, колонки длительности не было. Уже запущенный пользователем dev-процесс подхватил конфигурацию и применил development schema push: все 14 существующих записей получили 30 минут через default добавленной колонки. Скрипт после этого проверил реальные значения, обновил **0 дополнительных записей**, сохранил 14; повторное применение также обновило 0. Значения не обнулялись ради повторного заполнения. Итоговый read-only аудит: 14 записей, 14 значений 30, отсутствующих 0; остальные поля (включая updatedAt), 111 строк связей и 6 наград совпадают со снимком до изменения.

Повторяемый data-only скрипт:

```powershell
pnpm backfill:event-duration --check
pnpm backfill:event-duration --apply --backup D:\Backups\Evil\evil-before-event-duration-20261114-223721.dump
```

По умолчанию выполняется только проверка. Вывод: total/missing/updated/preserved/invalid/ids. Применение требует свежий (до 24 часов), непустой custom-архив вне репозитория с успешным `pg_restore --list`. Для последующего применения создайте новую актуальную копию.

Скрипт устанавливает `PAYLOAD_MIGRATING=true` до инициализации: не запускает generic schema push, миграции или сбросы. Если колонки нет, показывает необходимость безопасно применить добавочную схему Payload после backup и не пишет данные. Общий автоматически предложенный Drizzle-план содержал посторонние изменения ограничений; защитная проверка отказалась применять его. Схема вручную SQL не создавалась.

Заполнение читает сырые значения через Payload adapter, чтобы defaultValue не маскировал NULL. Транзакционный условный update заполняет только отсутствующее значение при совпадении id/updatedAt, сохраняет исходный updatedAt и не вызывает посторонние content hooks. Это доверенная локальная служебная операция; у adapter нет параметра overrideAccess. Существующие значения, включая некорректные, не перезаписываются; некорректные считаются отдельно. Повторные/одновременные применения проверены на отдельной тестовой базе.

## Ручная проверка и ограничения

1. `http://localhost:3000/admin/collections/events`: проверить длительность 30 и описание; изменить на другое положительное целое, проверить отклонение нуля/дроби. Использовать собственные проверочные записи.
2. `http://localhost:3000/events`: открыть ивент с расписанием, войти игроком, создать once; сверить выбранное время и зону. Отметить «Прошёл» так, чтобы КД достигал конца запуска; увидеть объяснение и перевыбор без молчаливого переноса. Отменить отметку до предупреждения и проверить тот же запуск.
3. `http://localhost:3000/account`: включить «Я играю», сохранить regular, проверить следующий подходящий запуск и отсутствие подходящих запусков в коротком периоде. Снять галочку КД: выбор запуска остаётся тем же. После изменения длительности в админке вернуться на вкладку игрока и проверить пересчёт.

Нет проверки фактической доступности игрового сервера. Конец расчётный, ивент может завершиться раньше. Отправка, Telegram, worker, cron и очередь не добавлены. Будущий обработчик обязан непосредственно перед отправкой заново проверить актуальные КД, длительность, расписание, состояние подписки и период игры; истёкшие предупреждения не догонять. Правила дедупликации из player-event-reminders.md сохраняются. Нет новых зависимостей или env-переменных. Ручную проверку админки с рабочими учётными данными выполняет пользователь.
