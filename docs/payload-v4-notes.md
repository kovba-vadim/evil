# Подготовка к Payload 4

Результаты статического аудита от 2026-11-02 для установленного Payload 3.92.1. Это заметки для будущего перехода, а не выполненная миграция. Совместимость с v4 не проверена; код, зависимости и база в рамках аудита не менялись. Тесты и проверки в админке не запускались.

Ориентир — [официальное руководство v3 → v4](https://payloadcms.com/docs/beta/migration-guide/v4). Перед переходом повторно сверить его актуальную редакцию. До отдельной задачи сохранять совместимость с установленной v3 и не переносить конфигурацию v4 заранее.

## Общий slug

- `src/fields/itemSlug.ts` использует публичный встроенный `slugField` из `payload`, источник — `name`. Общий helper подключён во всех девяти коллекциях со slug.
- Транслитерация выделена в `src/fields/slugifyItemName.ts`: чистая функция без импортов Payload, общая для сервера и клиентского поля.
- Helper через `overrides` перебирает дочерние поля `slugField`, находит `slug` и `generateSlug`, переопределяет хуки и клиентский компонент. Это зависимость от структуры и поведения штатного helper, хотя приватных импортов нет.
- Серверный `beforeValidate` сохраняет непустой явно переданный slug, при PATCH без непустого slug сохраняет существующий, иначе генерирует из названия. Хук `generateSlug.beforeChange` заменён на возврат `false`, чтобы штатная генерация не перезаписывала ручное или сохранённое значение.
- `src/fields/ItemSlugField.tsx` оборачивает публичный `SlugField` из `@payloadcms/ui` и добавляет автозаполнение новой записи через хуки формы. Сохранённая запись и ручное изменение отключают автоматическое следование названию.

При переходе перепроверить структуру результата `slugField`, порядок и поведение хуков, автозаполнение, ручной ввод, кнопку генерации, сохранение кириллического slug и частичные обновления. Существующие проверки в `tests/int/itemSlug.int.spec.ts` не доказывают совместимость с v4; нужна также проверка через Payload и локальную админку.

## Изображения и Sharp

В `src/collections/Media.ts` используется штатный `upload: true`. Нестандартная обработка изображений в хуках не обнаружена. В `src/payload.config.ts` Sharp подключён штатным для v3 верхнеуровневым свойством `sharp`.

По руководству v4 верхнеуровневое свойство `sharp` удаляется: будущий переход потребует официального `@payloadcms/transformer-sharp` и регистрации `sharpTransformer({ sharp })` в `upload.transformers`. Сейчас эту замену не выполнять. При миграции отдельно проверить загрузку, выдачу и доступ к файлам Media.

## Local API: результат исходного аудита и последующие изменения

На момент исходного аудита четыре CRUD-вызова ниже использовали значение по умолчанию `overrideAccess: true` в v3. По руководству v4 default меняется на `false`, поэтому эти вызовы могут изменить поведение без ошибки TypeScript.

| Файл и строка на момент аудита | Вызов | Что определить перед переходом |
| --- | --- | --- |
| `tests/int/api.int.spec.ts:15` | `payload.find`, коллекция `users` | Проверяется доступ пользователя или доверенное системное чтение? Для проверки прав нужны пользовательский контекст и явный `false`; для служебного чтения — обоснованный явный `true`. |
| `tests/helpers/seedUser.ts:16` | `payload.delete`, удаление прежнего тестового пользователя | Явно определить служебный режим подготовки теста. |
| `tests/helpers/seedUser.ts:26` | `payload.create`, создание тестового пользователя | Явно определить служебный режим подготовки теста. |
| `tests/helpers/seedUser.ts:38` | `payload.delete`, очистка тестового пользователя | Явно определить служебный режим очистки теста. |

Не проставлять `true` автоматически во всех запросах. В новых CRUD-вызовах выбирать значение явно по назначению операции. Тесты с созданием и удалением записей запускать только на явно выделенной тестовой базе.

Для полноты: все 14 CRUD-вызовов в `src/hooks/` уже имеют явные `overrideAccess: true`, передают `req` и `depth: 0`; они проверяют существование связей и защищают от удаления используемых записей. Вызов `payload.auth({ headers })` в `src/app/(frontend)/page.tsx` не принимает `overrideAccess` и к смене default CRUD не относится.

## Остальные результаты аудита

Все восемь полей `description` (включая добавленное позже описание ordinary-items) используют `richText` и глобальный `lexicalEditor()` из `src/payload.config.ts`, без локальных редакторов. Slate не найден в исходниках, `package.json` и `pnpm-lock.yaml`.

Внутренние импорты Payload не обнаружены: используются публичные корневые и subpath-экспорты. При обновлении import map следует перегенерировать штатной командой, а не редактировать вручную.

При итоговой подготовке проверок api.int.spec.ts переведён на защищённую тестовую базу и явный overrideAccess: true для служебного smoke-теста. Три вызова в e2e seedUser.ts остаются неявными; эти e2e не запускаются командой pnpm test:model и не должны запускаться на рабочей базе. Новые интеграционные проверки выбирают false для действий пользователя и true только для подготовки/очистки фикстур. Совместимость с v4 по-прежнему не проверена.
