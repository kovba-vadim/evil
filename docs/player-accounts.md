# Аккаунты игроков — первый этап

Реализованы `/register`, `/login`, `/account`, `/forgot-password`, `/reset-password`; POST `/api/account/{register,login,logout,profile,password,forgot,reset}`. Пять SEO Globals находятся в группе «Публичные страницы», страницы вызывают `public-seo.ts` и исключены из индексации. Кабинет требует серверную сессию.

## Модель и безопасность

Отдельная auth-коллекция `players`: email и пароль Payload, `nickname` (2–40 символов), `timeZone` из существующего списка зон. `users` остаётся административной коллекцией без новых ролей и переноса записей. Права Users, Media, служебных папок и игровых коллекций проверяют именно `req.user.collection === 'users'`. Прежнее включение папок Media сохранено; доступ к самим папкам ограничен администраторами через штатный collectionOverrides.

REST Players отключён (`endpoints: false`, ответ Payload 501), GraphQL Players отключён. Списка аккаунтов в публичном API нет. Local API с `overrideAccess: false` разрешает игроку читать/обновлять только свой документ. Email и `_verified` защищены field access. Hook запрещает игроку обновлять пароль без контекста серверной проверки текущего пароля. Внешние операции принимают только явно перечисленные поля; клиентские ID, права и overrideAccess игнорируются. Доверенные create регистрации и токенные forgot/reset используют обоснованный `overrideAccess: true`.

Криптография, JWT, сессии, проверка текущего пароля и reset-токены — штатные Payload. Cookie игрока `evil-player-token`: HttpOnly, SameSite=Lax, Path=/, 2 часа, Secure в production. Токенов в localStorage и ответах API нет, cookie администратора не перезаписывается. Logout отзывает сессию; смена пароля с проверкой текущего пароля отзывает все сессии. Reset-токен действует 30 минут, после успеха повторное применение отклоняется, прежние сессии отзываются. Автовход после reset не выполняется.

Все POST требуют JSON и точного Origin. Внешние returnTo, пути админки/API и циклы входа отбрасываются; ссылка входа запоминает текущий внутренний путь. Ответы API — no-store; reset-страница и ответы API задают no-referrer. Внутренние ошибки клиенту не раскрываются.

Защита от попыток: постоянный lockout Payload после 5 неверных входов на 15 минут; дополнительно 3 регистрации/восстановления и 10 входов на email за 15 минут, общий предел 300 POST за 15 минут на процесс. Память ограничена 10 000 ключами. X-Forwarded-For не считается доверенным идентификатором. Счётчики процесса сбрасываются при рестарте и не общие для нескольких workers. Перед масштабированием нужен общий limiter/proxy; текущий этап рассчитан на локальный Node.

## Почта и режимы

Почтового адаптера нет; SMTP, OpenServer и внешние сервисы не добавлены.

- Только `NODE_ENV=development`: `auth.verify=false`, регистрация сохраняет `_verified=false`, вход разрешён без подтверждения. Стандартные `baseVerificationFields` сохраняют одинаковую схему в development и production.
- Восстановление даёт одинаковый ответ для существующего/неизвестного email; для существующего аккаунта ссылка выводится **только в серверный терминал development**, никогда в API.
- В production/test `auth.verify=true`. Дополнительные beforeLogin и проверка сессии отклоняют неподтверждённый email. Нет env-флага, позволяющего включить локальный обход в production.
- Пока доставки нет, production-регистрация и запрос восстановления **явно возвращают 503** до работы с аккаунтами, без вывода ссылок. Это не готовая production-доставка. Для включения нужен отдельный этап: email-адаптер, подтверждение email и снятие серверной блокировки после проверок. Подтверждённые аккаунты могут входить в production.

## Интерфейс и время

Новые формы используют БЭМ и `account.scss`, существующие цвета, адаптивную оболочку, label/autocomplete, серверную валидацию, status/alert и блокировку повторной отправки. Добавлен только прямой Sass **1.77.4**, уже присутствовавший транзитивно в lockfile; версии существующих зависимостей не обновлены.

После входа зона аккаунта применяется к существующему `evilisland-time-zone`/setTimeZone store. Сохранение профиля обновляет тот же store. Выбор зоны в расписании остаётся локальным предпочтением до явного сохранения в кабинете. UTC+3, DST, данные и расписания не менялись.

В текущем коде нет сохранённых личных прохождений/КД: показывается справочный cooldown ивента/квеста. Перенос отметок не выполнялся.

## База, переменные и команды

Режим прежний — development schema push. Добавляются Players, её сессии и пять SEO Globals. Существующие Users/Media/игровые записи не преобразуются. Перед `pnpm dev` сохраните резервную копию PostgreSQL и проверьте добавочную схему; не подтверждайте reset, удаление/переименование существующих таблиц/колонок. Production schema push не включён, переход на миграции и развёртывание — отдельная задача.

Переменные без секретных значений: существующие `DATABASE_URL`, `PAYLOAD_SECRET`; для проверок с записью — `EVIL_TEST_DATABASE_URL` (отдельная база, имя заканчивается `_test`). NODE_ENV задаёт Next. Браузерный конфиг сам задаёт `PAYLOAD_MIGRATING=true`, `EVIL_ACCOUNT_BROWSER_TEST=true`: порт 3101, отдельный `.next/accounts-test`, рабочий dev-сервер не останавливается. Перед браузерными тестами примените схему только к тестовой базе модельными проверками. Тестовый флаг для обычного запуска не нужен.

```powershell
pnpm install --frozen-lockfile
pnpm generate:types
pnpm generate:importmap
pnpm exec tsc --noEmit
pnpm lint
pnpm test:int
pnpm test:model
pnpm exec playwright test --config playwright.accounts.config.ts
pnpm dev
```

Безопасный production build в отдельном PowerShell-процессе, без изменения .env:

```powershell
$env:DATABASE_URL='postgresql://unavailable:unavailable@127.0.0.1:1/evil_build_unavailable'
$env:PAYLOAD_MIGRATING='true'
pnpm build
```

## Ручной сценарий

1. Гостем открыть `/account`: переход на вход. Зарегистрировать временный аккаунт; проверить ошибки email, ника, короткого/несовпадающего пароля и повторного email. Войти, проверить навигацию.
2. Сохранить ник и зону, перезагрузить. Email только для просмотра. Перейти в расписание: зона общая, данные ивентов прежние.
3. Сменить пароль с неверным, затем верным текущим паролем. Проверить выход всех сессий и вход новым паролем. Выйти, проверить защиту кабинета.
4. Восстановить пароль по ссылке из серверного терминала development; повторная/истёкшая ссылка не действует. Запрос неизвестного email имеет тот же ответ.
5. Проверить клавиатуру, desktop/mobile и обе темы. Игрок не входит в `/admin`; существующий администратор по-прежнему входит отдельной сессией и редактирует контент. В админке проверить пять SEO Globals и сохранность Media/папок.
6. В production проверить 503 регистрации/запроса восстановления, отказ неподтверждённого email, Secure-cookie подтверждённого аккаунта и отсутствие recovery-ссылок в логах/ответах.

## Будущие этапы — только требования

Аккаунт будет хранить личные прохождения и КД. Напоминания бывают разовыми и регулярными; регулярные действуют во время режима «Я играю». Пользователь выбирает ивенты и время предупреждения. Личный КД не исключает запуск из напоминаний: по желанию показываем окончание КД и его отношение ко времени начала ивента. Длительность ивента для этого не нужна. Первый канал — Telegram. Провайдеры входа, очередь, режим игры, отметки и напоминания сейчас не реализуются, пустых разделов/кнопок нет.

## Результаты проверок и файлы

На выделенной EVIL_TEST_DATABASE_URL: `pnpm test:int` — 126/126; `pnpm test:model` — 76 сценариев с ожидаемым результатом (72 обычных успешных, четыре прежних it.fails для дефекта native join). После ограничения служебных папок отдельно повторены все шесть проверок Players — успешно. Проверены собственный/чужой профиль, запрет Users/Media/папок/игровой записи, защита email/verification/пароля, локальный JWT без подтверждения, блокировка после пяти ошибок, прежний вход администратора, отзыв сессий, повторная и истёкшая reset-ссылка.

Браузер Headless Edge: development lifecycle — 1/1 (регистрация → вход → редактирование → смена пароля с проверкой текущего → выход → восстановление), production account + shell — 4/4. Проверены HttpOnly/SameSite, cross-origin 403, закрытый Players API, 503 production, защита кабинета, returnTo, обе темы и ширины 1280/375 без переполнения. Снимки кабинета просмотрены. TypeScript, production build с недоступной БД, генерация типов/import map — успешно. Lint: 0 ошибок, три прежних предупреждения. В production-браузерном прогоне сервер также выводил `The destination stream closed early`; четыре сценария прошли, причина этого сообщения отдельно не установлена.

Не проверялись реальная доставка почты (адаптера нет), production-развёртывание, распределённые лимиты, реальный рабочий контент и админка с существующими учётными данными пользователя. Административный вход проверен временной фикстурой через Payload; визуальную проверку реальной админки/SEO/Media выполните вручную по сценарию выше. Тесты не подключались к рабочей базе для записи. Сбросов БД, push, merge и развёртывания не выполнялось.
