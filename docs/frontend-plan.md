# Публичный фронтенд EvilIsland

## Область работ

Админка и модель данных уже работают. Их поведение, доступ, рецепты, ручной порядок и подключение к PostgreSQL сохраняются. Фронтенд развивается только по отдельным заданиям. Этот документ фиксирует согласованные требования целиком; реализованные этапы и их проверки описаны ниже. Последующие разделы реализуются только по отдельному заданию.

## Согласованные требования

Стек:
- существующие Next.js + Payload;
- shadcn/ui и Tailwind для публичного интерфейса;
- стандартные компоненты, нейтральное оформление, акцент indigo;
- без прежних Sass helpers и без внедрения FSD;
- светлая, тёмная и системная темы;
- по умолчанию системная, ручной выбор сохраняется.

Оболочка:
- Sidebar shadcn слева;
- на компьютере сворачивается до иконок;
- на телефоне открывается выезжающей панелью;
- EvilIsland вверху ведёт на главную;
- активный раздел выделен;
- элементы доступны с клавиатуры;
- подсказки у иконок в свёрнутом состоянии.

Меню строго в таком порядке:
1. Ивенты
2. Квесты
3. Ивент-боссы
4. Кастом одежда
5. Кастом оружие
6. Кастом предметы
7. Craft
8. Запуск ивентов

Главная:
- название, описание сервера Rich Text и необязательная картинка;
- в дальнейшем редактируются через Payload;
- новости, Telegram и дополнительные блоки пока не нужны.

Общие списки:
- карточки;
- пока показываем все записи без UI-пагинации
  и кнопки «Показать ещё»;
- при получении данных учитывать серверную пагинацию:
  нельзя молча возвращать только первую страницу.

Глобальный поиск:
- по названиям ивентов, квестов, боссов, кастомных предметов,
  сетов, одежды, оружия и обычных ресурсов;
- результаты с подписью типа и ссылкой на страницу;
- кнопка открытия, Ctrl+K / Cmd+K;
- без поиска по полным описаниям;
- отдельные локальные поиски пока не нужны.

Ивенты:
- карточки: название, короткое описание, монеты,
  возможные предметы награды;
- сначала видны все;
- фильтр монет: слайдер с двумя ползунками
  и синхронизированные поля «От» / «До»;
- границы слайдера из полного каталога,
  не меняются от текущего результата фильтра;
- несколько кастомных предметов в фильтре:
  нужны ВСЕ выбранные предметы в возможных наградах;
- условия работают одновременно;
- число результатов, сброс, состояние «Ничего не найдено»;
- страница ивента: полное описание, награды с количеством,
  все времена запуска и КД;
- предметы наград ведут на свои страницы.

Запуск ивентов:
- каждый запуск отдельной строкой, по времени;
- по умолчанию ближайшие 24 часа от текущего момента;
- фильтры времени, монет и кастомных предметов;
- границы включены, переход через полночь поддерживается;
- порядок начинается с начала выбранного диапазона;
- select часового пояса, по умолчанию серверный UTC+3;
- ручной выбор сохраняется в localStorage;
- выбранный пояс используется для отображения времени
  и интерпретации фильтра, также на странице ивента;
- исходное расписание в базе остаётся UTC+3.
Точный набор часовых поясов уточнить перед реализацией раздела.

Квесты:
- карточки с названием, необходимым количеством,
  наградами и текстовым КД; пустые поля не показывать;
- фильтр категории;
- монеты от–до;
- фильтр по нескольким наградам из кастомных предметов
  и обычных ресурсов: нужны все выбранные;
- все условия одновременно;
- отдельная страница с полным описанием.
Будущую дополнительную группировку пока не делать.

Ивент-боссы:
- карточки с картинкой, названием и наградами;
- отдельная страница с описанием и ссылками на награды;
- без фильтров.

Кастом одежда:
- сначала группа карточек сетов, затем группа хазматов;
- без вкладок и фильтров;
- сет: описание и части одежды со ссылками;
- часть одежды и хазмат: описание, картинка и рецепт;
- использовать актуальную модель: связь с сетом
  заполнена у его части, пустая у хазмата.

Кастом оружие:
- карточки с картинкой и названием;
- отдельная страница с описанием и рецептом;
- без фильтров.

Кастом предметы:
- карточки с картинкой и названием;
- страница: описание, картинка;
- «Где получить»: связанные ивенты, квесты и боссы;
- собственный рецепт, если craftable;
- «Используется в крафте»: связанные ресурсы,
  одежда и оружие, где предмет — ингредиент;
- обратные списки автоматически из существующих связей.

Craft:
- общий список всех craftable из resources, clothing, weapons;
- без категорий, вкладок и фильтров;
- сеты как целое сюда не входят;
- ссылки на канонические страницы предметов,
  отдельные дубли страниц для Craft не создавать;
- порядок между разными коллекциями уточнить
  перед подключением этого раздела.

Рецепты:
- ингредиенты: картинка, название, количество;
- отдельно стоимость в монетах;
- ссылки на страницы кастомных предметов
  и обычных ресурсов.

Обычные ресурсы:
- отдельные страницы с картинкой и Rich Text описанием;
- доступны из рецептов, наград и глобального поиска;
- без собственного пункта меню.

## Первый этап

- Существующие Next.js и React не обновлять без необходимости. Добавить Tailwind и стандартные компоненты shadcn/ui через pnpm.
- Изолировать публичные CSS/reset, тему и провайдеры в route group (frontend), не подключать их к (payload).
- Создать адаптивную оболочку, sidebar, активный пункт меню, доступные кнопки, подсказки в свёрнутом состоянии и три режима темы с сохранением выбора.
- Главная — только заголовок EvilIsland. Разделы меню — заголовок и «Раздел в разработке». Без выдуманных данных.
- Не добавлять поиск, игровые запросы, фильтры, страницы записей, часовые пояса, Global главной, авторизацию посетителей или изменение доступа.
- Проверить TypeScript, lint, production build и по возможности браузер на desktop/mobile. Не допускать подключения или schema push рабочей базы при проверках.
- Коммит, push и публикация не выполняются.

## Открытые вопросы перед следующими этапами

- Публичное чтение текущего каталога и источников явно разрешено для семи коллекций (третий этап ниже). Остальные игровые справочники открывать только отдельными заданиями; Users публично не открывать. Не обходить доступ через overrideAccess: true.
- Global контента главной реализован отдельным этапом ниже: homepage, публичное чтение и SSR. Следующие игровые разделы остаются отдельными задачами.
- Канонические URL resources и ordinary-items закреплены ниже; URL записей остальных разделов и представление глобального поиска — отдельные этапы.
- Native join-пагинация в Payload 3.92.1: учитывать ограничения из model-verification.md и использовать проверенные прямые обратные запросы.

### Ручной сценарий

1. Запустить pnpm dev и открыть главную: заголовок EvilIsland, слева меню в согласованном порядке. Перейти во все восемь разделов и проверить заголовок и честную заглушку.
2. На широком экране свернуть меню, перейти между иконками клавиатурой: видны подсказки, активная ссылка выделена. Развернуть; название EvilIsland ведёт на главную.
3. В меню темы выбрать светлую и тёмную, перезагрузить страницу. Затем выбрать системную и изменить оформление ОС — сайт следует за системой.
4. На узком экране открыть меню, закрыть Escape и проверить возврат фокуса. Повторить закрытие кнопкой и переходом в раздел. Горизонтального переполнения нет.
5. На обычном локальном запуске отдельно убедиться, что админка Payload выглядит как раньше. Её root layout, CSS и providers в этой задаче не менялись.

## Второй этап: главная из Payload

Реализован Global `homepage` («Главная страница»): обязательный title по умолчанию EvilIsland, необязательные description (richText с глобальным Lexical) и image (upload → Media). Конфигурация — src/globals/Homepage.ts. Нет блоков, новостей, Telegram и самостоятельно заполненного рабочего контента.

Публичное чтение разрешено явно; update — существующая проверка authenticated для коллекции Users. Права Users, Media и игровых коллекций не менялись. src/queries/getHomepage.ts вызывает findGlobal с depth: 1, user: null и явным overrideAccess: false; это тот же запрос, который выполняет главная. Media заполняется с соблюдением его существующих прав.

Главная — async Server Component с dynamic = force-dynamic. На каждом запросе выполняется Local API; нет статического снимка, React cache, unstable_cache, ревалидационных hooks или специальных тегов. Ошибки чтения пробрасываются в стандартную обработку Next.js, без catch с пустым объектом или подменой успешной пустой страницей. После сохранения новое содержимое видно при следующем запросе/обновлении браузера; автоматического live-обновления открытой вкладки не добавлено.

src/components/public/homepage-content.tsx использует официальный RichText из @payloadcms/richtext-lexical/react установленной версии 3.92.1. Собственного преобразования Lexical в HTML и dangerouslySetInnerHTML нет. Публичные стили ограничены .public-app .homepage-richtext: заголовки, абзацы, маркированные/нумерованные списки и ссылки с indigo-акцентом в обеих темах. Используется next/image и существующий локальный media endpoint. Нет описания/картинки — соответствующий элемент не выводится. Проверены обычные URL-ссылки; ссылки Lexical на внутренние документы требуют согласованных канонических страниц, пока они не реализованы.

### PostgreSQL и применение схемы

Режим прежний: development schema push, без добавления миграций и без смены подключения. Добавляется таблица Global homepage. Агент применял схему только к выделенной тестовой базе. Рабочая база, её контент и .env не менялись. Перед обычным локальным запуском сохранить резервную копию PostgreSQL; при pnpm dev проверить добавочную схему, не подтверждать сброс, удаление существующих таблиц/колонок или их переименование. Production-переход на миграции остаётся отдельным этапом.

Типы сгенерированы pnpm generate:types. pnpm generate:importmap выполнен: новых импортов не потребовалось. Сгенерированные файлы вручную не редактировались. Зависимости в этом этапе не добавлялись/не обновлялись.

## Третий этап: кастомные предметы и обычные ресурсы

### Канонические маршруты (зафиксированы до реализации)

- `/items` — существующий каталог «Кастом предметы».
- `/items/[slug]` — единственная каноническая страница resources.
- `/ordinary-resources/[slug]` — минимальная страница ordinary-items без пункта меню и отдельного каталога.
- Источники events/quests/bosses и результаты clothing/weapons пока отображаются текстом: их отдельные страницы не реализованы. Существующие страницы-заглушки разделов не подменяют страницы записей.
- Результаты resources и кастомные ингредиенты ведут на `/items/[slug]`; обычные ингредиенты — на `/ordinary-resources/[slug]`. Дублей страниц Craft не создаём.
- Единый построитель ссылок src/lib/public-record-url.ts возвращает URL только для реализованных страниц записей; slug кодируется как один сегмент URL. Неизвестный slug — штатная 404 Next.js.

### Область доступа и запросов

Публичное чтение требуется только resources, ordinary-items, events, quests, bosses, clothing и weapons. Запись/удаление остаются Users. Users, equipment-sets, event-times и quest-categories публично не открываются. Поле recipe публично читается только у craftable; Users сохраняют возможность видеть и редактировать неактивный рецепт. Админское поведение и запреты удаления сохраняются.

Каталог и детальные страницы — SSR без кеширования. Все Local API вызовы страницы явно overrideAccess: false, user: null. Прямые обратные запросы, все страницы, порядок `_order` с устойчивым id при равенстве. Каталог выбирает только поля карточек; изображения загружаются пакетно. Деталь читает отношения на depth 0 и дозагружает ингредиенты и их картинки пакетами без их вложенных рецептов. Ошибки чтения не превращаются в пустые списки.

### Реализация и ограничения выборок

- src/lib/public-record-url.ts — единственный построитель URL записей. Src/queries/public-items.ts — типизированные публичные запросы и DTO для карточек, деталей, источников, ингредиентов и результатов. Sources events/quests/bosses выводятся без ссылок; results resources — с канонической ссылкой, clothing/weapons — без неё. Внутренние ссылки на записи в самом Lexical пока не разрешаются в канонические страницы; обычные URL-ссылки выводятся официальным рендерером как раньше.
- /items, /items/[slug], /ordinary-resources/[slug] — force-dynamic. Ничего не кешируется на уровне данных; изменения видны при новом запросе/обновлении. Нет UI-пагинации, фильтров, поиска, автозаполнения каталога или маршрутов записей других разделов. Неизвестные slug обрабатываются notFound(), HTTP 404 проверен.
- Порядок всех игровых списков — `_order`, затем id как устойчивый дополнительный ключ. Публичные вызовы явно user: null, overrideAccess: false. Все страницы выбираются до hasNextPage=false; pageSize по умолчанию 100 — размер порции, не предел результата. Тесты дополнительно используют страницы 1/2.
- Каталог выбирает только name/slug/image и id; Media читается одним пакетным запросом на порцию уникальных ID, по 200 ID максимум в in. При 12 карточках с одной картинкой проверено ровно 2 вызова find: каталог и Media. Filename включён в проекцию Media, так как Payload вычисляет URL из него.
- Деталь читается с depth: 0; ингредиенты resources/ordinary-items выбираются отдельными пакетами только с id/name/slug/image, без их рецептов и описаний. Картинки ингредиентов также пакетные. Отсутствующий документ ингредиента считается ошибкой данных, а не тихо исчезает; отсутствующая картинка даёт нейтральную заглушку.
- Обратное использование запрашивается прямо по recipe.resourceIngredients.resource AND craftable=true в resources/clothing/weapons. Native join не используется. Источники — прямые queries по rewards.resource; для bosses дополнительно учитываются временные goldenHeart/personalHeart, afterRead совместимости выдаёт количество 1. Неактивный собственный рецепт и неактивные результаты скрыты.
- Новый collection afterRead hideInactivePublicRecipe удаляет recipe из публичного ответа неактивных resources/clothing/weapons. Users и доверенные overrideAccess:true сохраняют исходные данные для админки и внутренних проверок. Структура recipe, его валидация, хранение и защита удаления не менялись. Условный field access здесь не используется: он блокировал проверку вложенного пути при публичном обратном запросе. Скрытие выполняется после обхода полей и не ломает query validation.
- Полная выдача всё ещё собирается в память, отдельный согласованный snapshot между запросами не создаётся. Большие каталоги/очень длинные списки источников нагрузочно не проверены; лимит по общему количеству не вводился. Состояние рабочего каталога не читалось и не менялось.

## Десятый этап: запуск ивентов и общий часовой пояс

Маршрут /event-launches теперь расписание, каждый реальный запуск — отдельная строка с датой, временем, названием/ссылкой /events/[slug], монетами и возможными предметами наград с диапазоном. Один ивент может присутствовать несколькими строками. Сортировка по Instant, при равенстве — ID ивента, а не по местному HH:mm или ручному порядку. POST /api/public/event-launches обновляет данные без навигации.

### Принятые правила времени

1. Исходные event-times.time остаются ежедневными HH:mm в фиксированном +03:00. Никаких записей или изменений схемы. Для каждой нужной серверной даты строится ZonedDateTime в +03:00 и затем Instant. Уже эти моменты, а не арифметика HH:mm, сравниваются с границами диапазона.
2. Без обеих границ — [now, now + 24 реальных часа]. Пустая пара означает этот режим, одна граница показывает подсказку и пока не ограничивает время; монеты/предметы продолжают действовать.
3. При заполненной паре начало строится на сегодняшней календарной дате выбранной зоны. Если этот момент строго раньше now, берётся следующая календарная дата; точное равенство now включено. Конец на той же дате, если До > От, иначе на следующей. От = До означает полные местные календарные сутки: при DST они могут длиться 23/25 реальных часов. Это отличается от режима ближайших 24 часов.
4. Обе границы включены. Ключ строки — eventID + epochMilliseconds запуска. Повторное добавление того же ивента в тот же реальный момент удаляется. Запуски на начальной и конечной границах полных суток, даже с одинаковым HH:mm, принадлежат разным датам и являются разными строками; они не сливаются. На обратном переводе часы могут выглядеть одинаково — даты и UTC-смещения показываются в каждой строке.
5. Для преобразования местных границ используется disambiguation:reject. Несуществующий или дважды встречающийся час ни в одной из границ не выбирается автоматически: возвращается понятная подсказка, строки временного диапазона не показываются до исправления. Если сегодняшний кандидат неоднозначен, он также не пропускается молча в пользу завтрашнего.
6. Смена зоны сохраняет введённые От/До и заново интерпретирует их. Сброс очищает время/монеты/предметы, но сохраняет общую выбранную зону. Завершённый диапазон привязан к ближайшему вхождению на момент запроса; сам по таймеру не перепрыгивает на завтра. Новое изменение фильтра/зоны или обновление страницы вычисляет ближайшее вхождение заново.
7. В rolling-режиме прошедшие строки удаляются клиентским тиком раз в секунду; новый горизонт/контент запрашивается раз в 30 секунд и при возврате фокуса. Часы основаны на серверном now + монотонном performance.now, не на часах/зоне браузера; медленный ответ не переводит их назад. Вкладки в фоне могут ограничивать таймеры; новый горизонт уточняется после возврата фокуса. Очистка диапазона отправляет свежий запрос, не возвращает давно устаревший SSR-снимок.

### Зоны и библиотека

Единственный список зон — TIME_ZONES в src/lib/time-zones.ts: сервер + города Европы, России, Кавказа, Центральной/Восточной Азии и США. Сервер — +03:00 без сезонного перевода, остальные — IANA. Select подписывает город и актуальное для now смещение; дата/время каждого запуска показывает смещение самого запуска. Новая зависимость @js-temporal/polyfill закреплена на 0.5.1; установлена с двумя новыми пакетами (polyfill и JSBI), существующие зависимости не обновлялись.

Причина: корректные календарные даты, отдельные Instant/ZonedDateTime и явное отклонение DST gaps/folds вместо собственного преобразователя смещений. Использованы [официальные правила Temporal](https://tc39.es/proposal-temporal/docs/timezone.html), [ZonedDateTime/disambiguation](https://tc39.es/proposal-temporal/docs/zoneddatetime.html), [README polyfill](https://github.com/js-temporal/temporal-polyfill) и [релиз 0.5.1](https://github.com/js-temporal/temporal-polyfill/releases/tag/v0.5.1). Polyfill импортируется явно, глобальный Temporal не заменяется.

Общий store/useTimeZone и TimeZoneSelect в src/components/public/time-zone.tsx используют localStorage evilisland-time-zone и события storage/изменения для синхронизации между экземплярами и вкладками. Неизвестное сохранённое значение нормализуется в server, при загрузке перезаписывается. Если storage недоступен, выбор живёт в памяти вкладки. SSR и первый hydration-render всегда используют явно подписанный server/+03:00 и один серверный timestamp. После hydration восстанавливается выбор; старые строки не показываются под новой зоной во время запроса. Зона окружения сервера/браузера автоматически не выбирается.

На /events/[slug] тот же store и select; EventLaunchTimes строит ближайшие реальные запуски из всех ежедневных времён и показывает их в выбранном поясе с датой/смещением. Не создаётся отдельная несовместимая настройка. КД остаётся отдельным полем.

### Фильтрация и компоненты

- src/lib/event-launches.ts — чистые launchWindow/expandLaunches с обязательным заданным now; тестируются без Payload и окружения.
- src/queries/public-launches.ts — getPublicSchedule/parseScheduleFilters. Монеты и ALL-предметы делегируются существующей findEvents, без временных from/to и без альтернативной логики наград. Затем пакетно читаются все связанные event-times, все страницы, по 200 ID в порции. Event DTO и предметы — существующий eventCards. Все Local API имеют overrideAccess:false,user:null; никаких запросов на каждую строку.
- src/components/public/launch-schedule.tsx — SSR-начало, общие Input/Slider/Button/EventRewards, фильтры часов/монет/предметов, счётчик запусков, сброс, ошибки и пустые состояния. Исходные пределы монет/предметы берутся из полного каталога ивентов, включая ивенты без launchTimes, не сужаются по результату. Debounce 300 мс, AbortController, номер запроса и привязка снимка к полному ключу фильтров/зоны исключают устаревшие ответы.
- src/components/public/event-launch-times.tsx — общий часовой пояс и экземпляры ближайших запусков в детали ивента.
- src/app/(frontend)/api/public/event-launches/route.ts — валидирует известную zone, HH:mm/пустые часы, целые монеты, положительные ID предметов. now и overrideAccess из клиента не принимаются. Неверный ввод — 400, ошибка данных — 5xx, не пустой список. Cache-Control:no-store. SSR и публичный endpoint используют серверное текущее now, детерминированные тесты передают его непосредственно функции.

Модель, PostgreSQL-режим, права, рабочее подключение и контент не менялись. Публичное чтение events/event-times/resources уже разрешено, запись остаётся Users. Полей/миграций/import map не добавлено, типы схемы не изменились.

### Ограничения

IANA-правила определяются timezone data Intl/ICU используемой среды; законодательные изменения требуют актуальной среды исполнения. Детерминированные тесты используют заданные даты/now, но различия версий tzdata для будущих реформ отдельно не эмулировались. Единственный fixed-offset вариант — server; произвольный ввод зон/городов не добавлен. На странице ивента показываются датированные ближайшие 24 часа, а не вечный перевод одного HH:mm для всех сезонов.

Серверный timestamp приходит со снимком; сетевая задержка может дать небольшое отставание отображаемых часов, это не NTP-синхронизация. Новый горизонт обновляется с интервалом до 30 секунд, прошедшие строки скрываются раз в секунду при активной вкладке. Полные range-результаты не опрашиваются по таймеру, остаются выбранным вхождением до изменения фильтра/перезагрузки. Списки собираются в память, большие каталоги нагрузочно не проверены, общей транзакции снимка нет. Native join-дефект остаётся и здесь не используется. Рабочая БД/контент не проверялись. Коммит и push не выполнялись.

## Одиннадцатый этап: глобальный поиск

GET /api/public/search?q=... — публичный endpoint только для чтения. Поиск только по name в восьми коллекциях SEARCH_TYPES: events, quests, bosses, equipment-sets, clothing, weapons, resources, ordinary-items. Ссылки — существующий publicRecordURL; новых страниц записей нет. UI на shadcn Dialog с установленным radix-ui и доступным combobox/listbox, без cmdk и новых зависимостей. Клиент не фильтрует серверную выдачу повторно.

Уточнение UX выбора времени отложено до наполнения ивентов реальными данными. На этапе поиска расписание, временные фильтры и правила диапазона не меняются.


### Реализация поиска

- `src/lib/search.ts`: единственный список восьми типов/русских подписей, DTO SearchResult/SearchResponse, минимальная длина 2 и максимальная 100 Unicode-символов после trim. Запрос другого типа, слишком длинный или с управляющими символами отвергается. Пустой/короткий запрос возвращает пустой ответ без инициализации Payload и без чтения БД; UI показывает начальную подсказку и не отправляет такой запрос.
- `src/queries/public-search.ts`: только name, без обыска описаний, рецептов и наград. Используется contains с литеральным экранированием %, _ и обратного слеша, case-insensitive PostgreSQL; ранжирование по приведённому к нижнему регистру названию: точное → префикс → остальное вхождение. При равной релевантности порядок SEARCH_TYPES, затем ID. Результаты с одинаковыми названиями/ID разных коллекций не сливаются, ключ kind:id.
- Ранжирование выполняется до отсечения: читаются все страницы совпавших name/slug (по 100, depth:0), в памяти удерживаются только шесть лучших кандидатов каждого типа. Шестой — признак more; в ответе максимум пять каждого типа, всего максимум 40. Позднее точное совпадение не теряется за первой страницей подстрочных совпадений. Внутренний размер страницы не является лимитом ответа. Payload 3.92.1 like разбивает запрос на слова, поэтому для точности буквального поиска/ранжирования он не используется. Raw SQL и внутренние импорты Payload не добавлены.
- Каждый вызов Local API имеет overrideAccess:false,user:null; серверный список коллекций закрыт для выбора из клиента и не содержит Users. select ограничен name/slug, DTO — key/id/kind/label/name/href. У bosses прежний forceSelect модели может дополнительно прочитать служебные legacy-зависимости наград внутри Payload; они не используются поиском и не передаются клиенту. Этот слой совместимости и модель по заданию не менялись. Join-поля equipment-sets не выбираются, native join не используется.
- `src/app/(frontend)/api/public/search/route.ts`: GET с единственным строковым q; повтор q — 400, неверная длина/управляющие символы — 400. Пустой/короткий — 200 с пустыми results/more. POST не реализован (405), запросы только для чтения. Ответ Cache-Control:no-store, ошибки БД остаются ошибками, не превращаются в отсутствие результатов.
- `src/components/ui/dialog.tsx`: минимальная необходимая часть shadcn Dialog на уже установленном radix-ui. `src/components/public/global-search.tsx`: доступный combobox/listbox с серверной выдачей, без cmdk и без повторной фильтрации результатов. Кнопка в AppSidebar расположена отдельно от восьми ссылок навигации; в свёрнутом виде иконка/tooltip. ShellContent владеет Dialog вне мобильной Sheet, поэтому поиск не размонтируется раньше корректного закрытия меню при выборе.
- Открытие кнопкой, Ctrl+K/Cmd+K (включая физический KeyK при русской раскладке), фокус в поле, стрелки вверх/вниз, Enter, Escape. Активный результат связан aria-activedescendant и прокручивается в видимую область. При закрытии фокус возвращается в исходный элемент; если мобильный триггер уже исчез, в кнопку меню. Выбор закрывает Dialog и мобильную Sheet, router.push ведёт на каноническую страницу. У результатов реальные href из общего helper, дополнительный prefetch деталей не выполняется.
- Debounce 300 мс, AbortController и номер запроса; состояние привязано к нормализованному запросу/повтору. Старые результаты не показываются для нового запроса; пустой ввод отменяет ожидание. Изменение только внешних пробелов не ломает ожидающий ответ. Начальная подсказка, загрузка, пустой ответ, ошибка и кнопка повторной попытки различаются; клавиатурный фокус после retry возвращается в поле. More перечисляет типы с дополнительными результатами и предлагает уточнить запрос.

## Завершение первого функционального этапа

В этап входят публичная оболочка с темами, главная из homepage, каталоги и детали предметов/одежды/оружия/сетов, Craft, ивент-боссы, ивенты, квесты, расписание с общим часовым поясом и глобальный поиск. Изменения, применимые тесты и документация фиксируются одним коммитом; push выполняется только по отдельному поручению.

Сводка оставшихся ограничений и отложенной работы:
- **Уточнение UX выбора времени отложено до наполнения ивентов реальными данными.** Текущие правила ближайшего вхождения, включительных границ, одинаковых часов и DST остаются зафиксированными в десятом этапе; в рамках завершения этапа они не меняются.
- Известный дефект native join PostgreSQL/Payload 3.92.1 остаётся: четыре it.fails воспроизводят его, а не подтверждают исправление. Публичные обратные списки используют прямые запросы с полной пагинацией.
- Большие каталоги, ID-пересечения и поисковая выдача нагрузочно не проверены. Полные каталоги/промежуточные ID собираются в память. Поиск читает страницы всех совпавших имён для правильного ранжирования, хотя ответ ограничен 40 строками. Полнотекстового индекса, морфологии и транслитерации поиска нет.
- Между несколькими запросами не создаётся общий транзакционный снимок. Фильтры не сохраняются в URL; границы/варианты выбора и сброс используют исходный SSR-снимок до обновления страницы.
- IANA-правила зависят от timezone data среды исполнения. Горизонт ближайших запусков обновляется до 30 секунд, прошедшие строки скрываются раз в секунду в активной вкладке; фоновые таймеры и сеть могут вносить задержку. Явно заданный диапазон остаётся выбранным вхождением до изменения фильтров/перезагрузки.
- Модельный слой совместимости прежних наград боссов и числового КД квестов сохранён. Завершение переноса и удаление legacy-полей — отдельная задача с проверкой backfill; автоматическое удаление колонок через schema push не выполняется. Совместимость с будущей Payload v4 не объявляется проверенной.
- Автоматические тесты с записью выполнялись только на EVIL_TEST_DATABASE_URL; агент не проверял реальный рабочий контент и не изменял рабочую БД. Сохраняются три прежних предупреждения lint в my-route и admin.e2e.spec.ts.
