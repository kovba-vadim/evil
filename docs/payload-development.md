# Payload: текущий этап и проверки

## Реализованный этап

Подключены `ordinary-items`, `resources`, `equipment-sets`, `clothing`, `weapons`, `event-times`, `events`, `quests`, `quest-categories` и `bosses`. Все операции этих коллекций доступны только аутентифицированным пользователям коллекции Users. Users и права Media сохранены. При использовании Local API от имени пользователя необходимо передавать `overrideAccess: false`: по умолчанию Local API обходит access control. Поля, целостность, будущий фильтр и сценарии проверки event-times/events описаны в [events-development.md](events-development.md). Новый этап quests/bosses и ручные проверки: [quests-bosses-development.md](quests-bosses-development.md).

Коллекции ordinary-items, resources, equipment-sets, clothing и weapons имеют обязательные название и уникальный slug, необязательное изображение Media. Общий `itemSlug()` использует встроенный `slugField` с `useAsSlug: 'name'` и обёрткой `ItemSlugField` над штатным клиентским полем. В Payload 3.92.1 штатный клиент генерирует только кнопкой Generate, а не при вводе названия. Обёртка подписывается на название и автоматически заполняет slug новой записи, пока пользователь не изменил его вручную. Unlock нужен только для ручного редактирования. После сохранения переименование не меняет непустой slug. Общая функция `slugifyItemName` транслитерирует русский текст, приводит к нижнему регистру и заменяет разделители на одиночные дефисы: «Шлем Evil» → `shlem-evil`. Существующие и вручную переданные непустые slug сохраняются как есть, без массовой нормализации.

Серверный hook slug `beforeValidate` заполняет пустой/отсутствующий slug из названия до required-валидации, в том числе при создании через API. Генерация не зависит от скрытого `generateSlug`; штатный beforeChange этого флага заменён, чтобы он не перезаписывал ручные и сохранённые значения. Уникальный индекс slug сохранён. Если название не содержит символов, из которых можно получить slug, нужно ввести корректный slug вручную; required-валидация остаётся включённой. У ordinary-items, resources, equipment-sets, clothing и weapons есть необязательное описание Lexical. Характеристики вводятся текстом; полей уровней нет.

У resources, clothing и weapons один вложенный `recipe`: `resourceIngredients` (resource + quantity), `ordinaryIngredients` (item + quantity), `coins`. Общие поля определены в `src/fields/recipe.ts`; существующая структура ресурсов сохранена. Поле `craftable` управляет активностью и видимостью рецепта. Выключение сохраняет рецепт. Неактивные рецепты исключаются из графа циклов, но их ссылки учитываются при удалении. Числа проверяются как безопасные целые JavaScript; количества положительные, монеты неотрицательные. Одежда и оружие не могут быть ингредиентами.

Общий хук перед сохранением проверяет ингредиенты и дубли по ID. Только для resources дополнительно проверяются циклы активных рецептов. Обход итеративный, с `depth: 0` и передачей `req`. Частичное обновление проверяется с учётом прежних полей группы; массив ингредиентов заменяется целиком. Обратное использование определяется запросами `recipe.resourceIngredients.resource` и `recipe.ordinaryIngredients.item`; второго редактируемого списка нет. Перед удалением ингредиента проверяются рецепты resources, clothing и weapons, включая неактивные; при наличии ссылок возвращается ошибка без каскадного удаления.

В clothing нет отдельного вида одежды: необязательная связь `equipmentSet` с одним equipment-sets определяет принадлежность. Сет выбран — часть выбранного сета; поле пустое — самостоятельный хазмат. Существование выбранного сета проверяется на сервере, частичные обновления учитывают прежнюю связь. Пояснение поля: «Для части комплекта выберите сет. Для хазмата оставьте пустым». Состав сета — штатное join-поле `parts` на `clothing.equipmentSet`, поддерживаемое установленной версией Payload (проверено по исходникам и при загрузке конфигурации генератором). Нет фиксированного числа частей и второго редактируемого массива. Перед удалением сета проверяются ссылки clothing.

Перед удалением прежнего `kind` сохранённые записи проверены прямым SELECT в PostgreSQL в транзакции READ ONLY, без инициализации Payload и schema push: в clothing 0 записей; `kind = 'set-part'` без `equipment_set_id` — 0. Данные и схема этой проверкой не изменялись. Удалено только поле kind из конфигурации; пути equipmentSet и recipe сохранены. При следующем development schema push удаление старой колонки kind ожидаемо; сброс базы, удаление связей или рецептов не требуются. Если до применения схемы появятся новые записи, проверку частей без сета нужно повторить перед удалением колонки.

Защита удаления изображений и изменения Media отложены до общей проверки игровых коллекций. Защита удаления кастомных предметов учитывает рецепты, награды events/quests, `bosses.rewards.resource`, а до завершения переноса — также прежние ссылки боссов. Обычные ресурсы также защищены ссылками из quests.ordinaryRewards.item, категории квестов — связями quests.category. Фронтенд и seed-данные не добавлены.

## PostgreSQL: development schema push

### Ручной порядок игровых коллекций

В ordinary-items, resources, equipment-sets, clothing, weapons, event-times, events, quests, quest-categories и bosses включён верхнеуровневый `orderable: true`. Для всех будущих игровых коллекций это также обязательная настройка. Users и Media не затронуты. Используется только встроенный механизм Payload 3.92.1: перетаскивание строк стандартного списка, служебное индексируемое текстовое поле `_order`, встроенный endpoint и fractional indexing. `_order` не нужно создавать или редактировать вручную. Payload сам устанавливает `defaultSort: '_order'`, если другая сортировка не задана; в этих коллекциях она не переопределяется. Для хронологического порядка event-times запрос явно задаёт `sort: 'minutes'`. Настройка orderable у join-поля состава сета отдельно не включается: задача касается общих списков коллекций.

Порядок хранится в БД и должен сохраняться после перезагрузки админки. В будущем запросы сайта могут явно передавать `sort: '_order'` (REST: `sort=_order`); для обратного порядка — `sort: '-_order'`. Учитывать пагинацию. Порядки разных коллекций независимы и не задают единый порядок смешанного каталога.

Существующие документы не пересоздаются, связи и рецепты не меняются конфигурацией. Development schema push добавит служебную колонку и индекс. Встроенный endpoint при первой попытке перестановки относительно записи без ключа сначала инициализирует порядок старых записей через штатные обновления Payload; после этого может потребоваться повторить перетаскивание. Эти обновления проходят обычные хуки и могут изменить updatedAt; начальный порядок старых записей до присвоения ключей не гарантирован. Собственный backfill и миграции не добавляются. Новые записи получают ключ в конце списка автоматически.

Ручная проверка после применения schema push: в каждой из пяти коллекций выбрать сортировку по ручному порядку (если ранее сохранена другая сортировка списка), переставить записи, обновить страницу и проверить сохранение порядка. Для старых записей учесть первую инициализацию и при необходимости повторить перенос. Проверить, что названия, slug, связи и рецепты остались прежними. Сохранение порядка через БД требует проверки на отдельной тестовой базе либо ручной проверки пользователем в админке; TypeScript и генерация типов этого не доказывают.

### Подключение и применение схемы

Сохранена существующая настройка `postgresAdapter`: `push` не переопределяется. Установленный адаптер выполняет schema push при подключении вне production, если `PAYLOAD_MIGRATING !== 'true'` и `push !== false`. Это также относится к инициализации Payload из тестов. `pnpm dev` после изменения конфигурации может обновить схему локальной базы.

Миграции сейчас не вводятся: файлов миграций и `prodMigrations` нет. В production автоматический development push не выполняется; развёртывание новой схемы в production этим этапом не настроено. Перед будущим переходом на миграции нужен отдельный описанный переход с учётом существующей схемы и данных. Сброс базы и разрушительные изменения не разрешены.

`pnpm generate:types` и `pnpm generate:importmap` работают с конфигурацией без инициализации подключения Payload к базе. Генерируемые файлы вручную не редактируются.

## Проверки без базы

После изменения конфигурации:

1. `pnpm generate:types`
2. `pnpm exec tsc --noEmit --incremental false`
3. `pnpm lint`
4. `pnpm generate:importmap`, если изменились компоненты полей (в том числе встроенный slug).

Эти проверки не доказывают поведение отношений и валидации через Payload/PostgreSQL.

## Проверки через Payload на отдельной тестовой базе

Выделенная тестовая PostgreSQL-база подключена; проверки через Payload выполнены. Итог и известный дефект join-пагинации — в [model-verification.md](model-verification.md). Подготовлены защищённый тестовый адаптер и команда pnpm test:model; порядок создания отдельной PostgreSQL-базы и покрытие описаны в [model-verification.md](model-verification.md). Рабочий DATABASE_URL не меняется и не используется тестовым адаптером. E2e-хелперы пока используют обычный конфиг: не запускать их на рабочей базе. Временные фикстуры допустимы только в выделенной тестовой базе; они не являются игровыми данными.

Проверить через Local API с `overrideAccess: false` и через REST:

- доступ ко всем игровым коллекциям с Users и запрет без авторизации;
- создание и PATCH, обязательность и уникальность slug, кириллицу и ручной slug;
- обычные, ресурсные и смешанные ингредиенты; бесплатный рецепт;
- пустой активный рецепт, нулевые/отрицательные/дробные количества, отрицательные/дробные монеты, дубли и отсутствующие ID;
- прямой цикл, цепочку из нескольких ресурсов, допустимое общее поддерево, выключение и повторное включение крафта;
- частичные обновления группы и замены массивов, сохранность скрытого рецепта;
- обратные запросы по обоим вложенным путям, запрет удаления при активных и неактивных ссылках и удаление после снятия всех ссылок; массовые операции;
- отсутствие частично сохранённых изменений после ошибки.

Дополнительно для equipment-sets/clothing/weapons проверить через Payload на тестовой базе:

- одежда сохраняется с существующим сетом и без сета; несуществующий сет отклоняется, в том числе при PATCH только связи;
- очистка equipmentSet превращает часть в самостоятельный хазмат; перенос части между сетами изменяет обратный состав обоих сетов; PATCH других полей сохраняет прежнюю связь;
- `parts` возвращает все части с учётом пагинации join, включая сет с числом частей больше размера страницы; никакого фиксированного игрового ограничения нет;
- рецепты clothing/weapons принимают только resources и ordinary-items, сохраняют неактивные данные и отклоняют те же ошибки чисел, дублей и ссылок;
- удаление кастомного предмета и обычного ресурса блокируется каждым из трёх типов результата, в том числе при неактивном рецепте;
- используемый сет не удаляется, а свободный удаляется без каскадного удаления одежды;
- регрессия resources: прежние рецепты, самоссылка и косвенный цикл, общие зависимости без цикла, выключение и повторное включение крафта.

## Ручная проверка админки пользователем

Без автоматического наполнения каталога пользователь может проверить на самостоятельно введённых записях:

1. Русские подписи, списки и поиск ингредиентов всех коллекций текущего этапа.
2. Автоматический slug из русского названия, ручное изменение и ошибку повторяющегося slug.
3. Необязательные изображение и описание; выбор Media и редактор Lexical.
4. Показ рецепта при включении крафта; сохранность после выключения, сохранения и повторного открытия/включения.
5. Сохранение допустимого рецепта и сообщения об ошибках количества, монет, повторов, пустого активного рецепта и циклов.
6. Запрет удаления ингредиента из активного и неактивного рецепта, затем удаление после снятия ссылки.

Для нового этапа отдельно:

1. Открыть сет и убедиться, что у него нет уровня и рецепта. Добавить несколько частей через clothing и проверить их появление в «Составе сета» после обновления. Проверить переходы по страницам состава при большом количестве частей.
2. Убедиться в отсутствии поля «Вид одежды». Сохранить одежду с выбранным сетом, перенести в другой сет и проверить оба состава.
3. Сохранить одежду с пустым «Сет» как самостоятельный хазмат. У части очистить «Сет», сохранить и убедиться в исчезновении из прежнего состава. Повторно выбрать сет и проверить возвращение в состав; существующие рецепты должны сохраниться при всех переключениях.
4. В clothing и weapons проверить смешанный рецепт, стоимость 0, сохранение выключенного рецепта и повторное включение. Повторить ошибки дробных/отрицательных значений, дублей и пустого активного рецепта.
5. Проверить запрет удаления ингредиентов, используемых только одеждой или только оружием, в том числе при выключенном крафте. После снятия всех ссылок удаление должно быть доступно.
6. Проверить запрет удаления используемого сета; после переноса или удаления его частей свободный сет должен удаляться. Связанные сущности не должны удаляться каскадно.
7. Повторить сохранение ранее созданных рецептов ресурсов и проверки циклов после выделения общих полей.

Для slug во всех девяти игровых коллекциях с itemSlug проверить на новой форме без сохранения: ввести «Шлем Evil» и увидеть `shlem-evil` без Unlock/Generate, затем изменить английское название и увидеть обновление. После Unlock ввести свой slug, изменить название и убедиться, что ручное значение осталось. На сохранённой записи переименование должно сохранять прежний slug. На отдельной тестовой базе проверить создание через API без slug, с пустым/пробельным slug, с ручным slug и конфликт уникальности. Эти записи не создавать на текущей базе.

Изолированные тесты `tests/int/itemSlug.int.spec.ts` проверяют транслитерацию, реакцию общей клиентской обёртки на изменение состояния формы (включая StrictMode), ручные/сохранённые значения и вызов серверных хуков. Они не инициализируют Payload и не обращаются к БД; штатное UI поля в тесте заменено заглушкой. Это не проверка сохранения через Local/REST API и не визуальная проверка живой админки.

Пользователь подтвердил, что основные коллекции созданы и проверены вручную. Это подтверждение относится к админке и не заменяет интеграционную проверку запросов, пагинации и прав через Payload/PostgreSQL; см. [model-verification.md](model-verification.md).

## Ограничения целостности

Стандартные хуки проверяют состояние, видимое в текущей транзакции. Они не дают строгой гарантии при конкурентных изменениях: два параллельных сохранения могут совместно образовать цикл; возможна гонка проверки удаления и создания ссылки. Собственные блокировки, SQL-триггеры и дополнительная инфраструктура не вводятся по принятому решению. Проверки через PostgreSQL и интерфейс админки остаются необходимыми; успешные TypeScript и lint их не заменяют.

## Награды боссов и подписи справочников

Ordinary-items отображается как «Обычные ресурсы», resources — «Кастомные предметы». Технические slug, таблицы и связи не переименованы. У ordinary-items добавлено необязательное описание richText с глобальным Lexical. Структура рецептов не меняется, обновлены только подписи. Боссы используют стандартный массив наград resource + quantity; безопасный переход со старых ссылок описан в [boss-rewards-transition.md](boss-rewards-transition.md).

Итоговая проверка через тестовую PostgreSQL выполнена; прямые обратные запросы с пагинацией работают. Штатная пагинация join на третьей странице имеет подтверждённый дефект адаптера 3.92.1. Подробности, обход прямыми запросами и ожидаемые падения тестов: [model-verification.md](model-verification.md).

Уточнение native join: сет из семи вещей полностью возвращается при текущем defaultLimit = 10. Для больших наборов стандартные списки с фильтром по equipmentSet/category используют прямые запросы; не следует автоматически считать их затронутыми дефектом native join. Минимальное воспроизведение, проверенный серверный findEvents и ограничения обходов: [model-verification.md](model-verification.md).
