# Payload: текущий этап и проверки

## Реализованный этап

Подключены `ordinary-items` и `resources`. Все операции новых коллекций доступны только аутентифицированным пользователям коллекции Users. Users и права Media сохранены. При использовании Local API от имени пользователя необходимо передавать `overrideAccess: false`: по умолчанию Local API обходит access control.

Обе коллекции имеют обязательные название и уникальный slug, необязательное изображение Media. Слаг создаётся встроенным `slugField` с возможностью ручного изменения; его опция `slugify` сохраняет Unicode-буквы, включая кириллицу. У resources есть необязательное описание Lexical.

У ресурса один вложенный `recipe`: `resourceIngredients` (resource + quantity), `ordinaryIngredients` (item + quantity), `coins`. Поле `craftable` управляет активностью и видимостью рецепта. Выключение сохраняет рецепт. Неактивные рецепты исключаются из графа циклов, но их ссылки учитываются при удалении. Числа проверяются как безопасные целые JavaScript; количества положительные, монеты неотрицательные.

Хук перед сохранением проверяет ингредиенты, дубли по ID и циклы активных рецептов. Обход итеративный, с `depth: 0` и передачей `req`. Частичное обновление проверяется с учётом прежних полей группы; массив ингредиентов заменяется целиком. Обратное использование определяется запросами `recipe.resourceIngredients.resource` и `recipe.ordinaryIngredients.item`; второго редактируемого списка и join-полей нет. Перед удалением ингредиента проверяются все рецепты ресурсов, включая неактивные; при наличии ссылок возвращается ошибка без каскадного удаления.

Защита удаления изображений и изменения Media отложены до общей проверки игровых коллекций. При добавлении clothing, weapons и наград нужно расширить проверки удаления соответствующими запросами. Фронтенд, остальные игровые коллекции и seed-данные не добавлены.

## PostgreSQL: development schema push

Сохранена существующая настройка `postgresAdapter`: `push` не переопределяется. Установленный адаптер выполняет schema push при подключении вне production, если `PAYLOAD_MIGRATING !== 'true'` и `push !== false`. Это также относится к инициализации Payload из тестов. `pnpm dev` после изменения конфигурации может обновить схему локальной базы.

Миграции сейчас не вводятся: файлов миграций и `prodMigrations` нет. В production автоматический development push не выполняется; развёртывание новой схемы в production этим этапом не настроено. Перед будущим переходом на миграции нужен отдельный описанный переход с учётом существующей схемы и данных. Сброс базы и разрушительные изменения не разрешены.

`pnpm generate:types` и `pnpm generate:importmap` работают с конфигурацией без инициализации подключения Payload к базе. Генерируемые файлы вручную не редактируются.

## Проверки без базы

После изменения конфигурации:

1. `pnpm generate:types`
2. `pnpm exec tsc --noEmit --incremental false`
3. `pnpm lint`
4. `pnpm generate:importmap`, если изменились компоненты полей (в том числе встроенный slug).

Эти проверки не доказывают поведение отношений и валидации через Payload/PostgreSQL.

## Проверки через Payload на отдельной тестовой базе

Явно выделенная тестовая база в текущем процессе не подтверждена. `test.env` не задаёт отдельное подключение; существующие конфиги тестов загружают обычный dotenv, а e2e-хелпер создаёт и удаляет пользователя. Не запускать тесты с записью на текущей базе. Для будущих тестов нужны отдельная PostgreSQL-база, явный выбор её подключения до импорта конфига и защита от случайного использования рабочей базы. Временные фикстуры допустимы только в ней; они не являются игровыми данными.

Проверить через Local API с `overrideAccess: false` и через REST:

- доступ к обеим коллекциям с Users и запрет без авторизации;
- создание и PATCH, обязательность и уникальность slug, кириллицу и ручной slug;
- обычные, ресурсные и смешанные ингредиенты; бесплатный рецепт;
- пустой активный рецепт, нулевые/отрицательные/дробные количества, отрицательные/дробные монеты, дубли и отсутствующие ID;
- прямой цикл, цепочку из нескольких ресурсов, допустимое общее поддерево, выключение и повторное включение крафта;
- частичные обновления группы и замены массивов, сохранность скрытого рецепта;
- обратные запросы по обоим вложенным путям, запрет удаления при активных и неактивных ссылках и удаление после снятия всех ссылок; массовые операции;
- отсутствие частично сохранённых изменений после ошибки.

## Ручная проверка админки пользователем

Без автоматического наполнения каталога пользователь может проверить на самостоятельно введённых записях:

1. Русские подписи, списки и поиск ингредиентов обеих коллекций.
2. Автоматический slug из русского названия, ручное изменение и ошибку повторяющегося slug.
3. Необязательные изображение и описание; выбор Media и редактор Lexical.
4. Показ рецепта при включении крафта; сохранность после выключения, сохранения и повторного открытия/включения.
5. Сохранение допустимого рецепта и сообщения об ошибках количества, монет, повторов, пустого активного рецепта и циклов.
6. Запрет удаления ингредиента из активного и неактивного рецепта, затем удаление после снятия ссылки.

## Ограничения целостности

Стандартные хуки проверяют состояние, видимое в текущей транзакции. Они не дают строгой гарантии при конкурентных изменениях: два параллельных сохранения могут совместно образовать цикл; возможна гонка проверки удаления и создания ссылки. Собственные блокировки, SQL-триггеры и дополнительная инфраструктура не вводятся по принятому решению. Проверки через PostgreSQL и интерфейс админки остаются необходимыми; успешные TypeScript и lint их не заменяют.
